# Grokky — architecture and quality audit, 2026-08-03

Full review of the Grokky package: how it works, everything it is connected to, what is
wrong with it, what the platform does not give it, and what to do about it — measured
against current published practice for LLM agents. **No code was changed.** Every claim
below was re-checked against source after it was first raised; claims that did not survive
are listed in [Appendix A](#appendix-a--claims-that-did-not-survive) so they are not
re-litigated.

---

## 1. Method and confidence

Two passes. The first read every file in `src/`, `dockerfiles/`, `docs/`, `files/` and
`css/`, mapped the seams into Dart core and other packages, root-caused the three
user-reported failures, and researched current best practice on the web. The second pass
took every critical/high finding and tried to **refute** it against the code, and separately
tried to disprove each claimed platform-API gap by finding the API.

| | Raised | Survived |
|---|---|---|
| Findings | 250 | 61 confirmed, 24 partial, 11 duplicates, 1 refuted (of 97 adversarially re-checked; the rest are medium/low and carry first-pass confidence only) |
| Missing platform APIs | 83 | 38 real gaps, 12 partial, **12 already exist** (Grokky is reimplementing platform functionality) |
| Best practices researched | 29 | with sources, each scored against Grokky's actual code |

Severity is **user-facing**: `critical` = data loss, security, or a wrong answer the user
will act on; `high` = fails in realistic use; `medium` = degraded quality or a maintenance
trap; `low` = polish. Several first-pass severities were corrected downward during
verification — those corrections are kept.

## 2. Verdict

**Grokky's discovery and context architecture is genuinely ahead of published practice. Its
action, verification, and trust architecture is behind it. Both reported failure classes come
from the second.**

What is very good, and should be protected:

- **The four static view meta-tools** ([src/ai/view-tools.ts:245-286](../src/ai/view-tools.ts)) —
  hundreds of per-view `DG.Func`s are never declared to the model; it searches them. The defs
  are module constants so the prompt prefix stays byte-stable and cacheable. This is exactly
  the progressive-disclosure pattern Anthropic published, arrived at independently.
- **The five op-dispatch MCP tools** ([dockerfiles/mcp-server/src/ops.ts](../dockerfiles/mcp-server/src/ops.ts)) —
  32 tools collapsed to 5, measured: 3,847 → 1,061 tokens/call, with no capability lost
  because an op-less call returns the domain schema.
- **The act→verify gate** ([dockerfiles/claude-runtime/src/verify.ts](../dockerfiles/claude-runtime/src/verify.ts)) —
  a `Stop` hook that refuses to let a turn end while an action is unproven is ahead of every
  comparable product surveyed. The *idea* is right; the *implementation* is what failed.
- **The benchmark harness** ([src/ai/benchmark/benchmark.ts](../src/ai/benchmark/benchmark.ts),
  [docs/BENCHMARK.md](BENCHMARK.md)) — real pipeline, TTFT/cost/tool-order/unverified-rate,
  deterministic asserts plus a majority-vote judge. Better than most teams have.

What is structurally wrong:

1. **The cheapest way for the model to do anything is to write JavaScript that the browser
   `eval`s.** Everything downstream follows from this: verification must be model-authored
   (nothing else knows what an arbitrary string intended), permissioning must be all-or-nothing
   (there is no operation identity to gate on), audit is a truncated string in the user's own
   IndexedDB, and undo is impossible. The platform learns nothing from each execution, so the
   next user's identical request regenerates the same code with different bugs.
2. **The model grades its own homework.** Both reported failures are the same bug seen from
   two sides: a false negative (correct action, "Not verified") and a false positive (nothing
   persisted, "Data Sync is ON"). A self-authored assertion proves the model's belief, not the
   world.
3. **The knowledge that teaches the model is not tested.** The skills contain a fabricated
   function tag, a wrong enum that silently produces an all-null column, a project-save recipe
   that *destroys* server-side data-sync configuration, and 74 fenced blocks teaching an
   execution mechanism the browser no longer honors.
4. **The security posture does not match the README.** `CLAUDE.md:19-21` says "safe, secure,
   governed, monitored and measured". Verified: not governed (`canUseTool` allows everything),
   not monitored (no server-side audit of executed code), not measured (quota hardcoded to
   1000/day for everyone, cost metrics computed and discarded).

Nothing here says the product direction is wrong. It says the scaffolding under a good idea
needs to be built before the surface area grows further.

## 3. How Grokky actually works

The package `CLAUDE.md` is broadly accurate but has drifted in specific, load-bearing ways
(see [§6.7](#67-documentation-drift)). This is the verified picture.

```
Browser (this package)                     Datagrok server        Containers (this package)
┌──────────────────────────┐               ┌────────────┐         ┌───────────────────────┐
│ AIPanel (singleton)      │               │            │         │ grokky-claude-runtime │
│  └ runPromptWithLifecycle│──WS /ws──────▶│ docker     │────────▶│  Hono + agent-sdk     │
│      grok.ai.processPrompt│   proxy       │ proxy      │         │  ├ session.ts (turns) │
│      UsageLimiter        │               │            │         │  ├ verify.ts (gate)   │
│      streamOnce          │◀──chunk───────│            │◀────────│  ├ prompts.ts         │
│                          │◀──input_request│           │         │  ├ sync/ (skills,     │
│ executeSingleBlock       │───response────▶│           │         │  │   help, packages)  │
│   new Function(grok,ui,  │               │            │         │  └ plugin/skills/*.md │
│     DG,view,t)           │               │            │         └───────────┬───────────┘
│ runVerification          │               │            │              MCP    │ HTTP
│ view-tools (4 meta-tools)│               │            │         ┌───────────▼───────────┐
│ ConversationStorage (IDB)│               │  REST API  │◀────────│ grokky-mcp-server     │
└──────────────────────────┘               └────────────┘         │  5 op-dispatch tools  │
                                                                  └───────────────────────┘
```

**One panel, one session.** `initAIWindow()` creates a single `AIPanel` mounted into
`grok.shell.windows.ai` (the Dart `xpAIPanel`). It survives view switches; every prompt gets
a fresh `buildWorkspaceContext()` snapshot instead. Ribbon icons on table/script/query views
toggle this one panel.

**A prompt's path** ([src/ai/ui.ts:244](../src/ai/ui.ts)): `!`/`!!` bash escape → `grok.ai.processPrompt()`
(the Dart sync interpreter gets first refusal; a claimed prompt never reaches the model) →
`UsageLimiter` → `streamOnce()` → WebSocket `user_message` carrying `grok.dapi.token`, the MCP
URL, and the four client tool defs.

**Actions come back as questions.** The runtime registers browser-executed tools
(`datagrok_exec`, `datagrok_verify`, `datagrok_show_entities`, and the four view tools) with
the SDK; when the model calls one, the runtime emits `input_request` to the browser, the
browser executes and replies `input_response`. **There is no fenced-block execution any more** —
`executeSingleBlock` has exactly three callers, and none of them parses the final markdown.

**Verification** ([verify.ts](../dockerfiles/claude-runtime/src/verify.ts)): a `PostToolUse` hook
marks the turn as owing proof after any `datagrok_exec` or non-read MCP call; a `Stop` hook
refuses to end the turn until a `datagrok_verify` returns `{passed: true}`, up to 3 blocks,
after which `final` carries `unverified: true` and the panel shows the red banner.

**Deployment asymmetry that matters.** `dockerfiles/*/src` compiles **inside the image**
(`Dockerfile`: `COPY src ./src` → `npx tsc` → `rm -rf src`). `grok publish` rebuilds only the
browser bundle. So any fix spanning both halves is only half-deployed until the image is
rebuilt — and **nothing in the protocol lets either side detect the skew**.

## 5. The three reported failures

### 5.1 "Data Sync is ON" — it was never on, and the save can destroy an existing sync

**The user's report.** Grokky opened `demog.csv`, set `df.tags['.data-sync'] = 'true'`, saved
a project, reported success, "verified" it, and only admitted on the third challenge that the
server-side `TableInfo` had zero tags.

**Ground truth, from core.** Data sync is not a flag you set; it is a *contract with a
creation script*:

1. `DataFrame.tags` and `TableInfo.tags` are **different maps**. `grok_TableInfo_Get_Tags`
   returns Dart `metaParams` (`grok_api.dart:812`), while `TableInfo.fromTable` copies only tag
   **keys**, never values: `..tags = t.tags.keys.toSet()` (`table_info.dart:61`). So
   `df.tags['.data-sync']='true'` → `df.getTableInfo()` → **the value is gone before the save
   even starts**.
2. The server requires the literal `'sync'`, not `'true'`: `t.metaParams[Tags.DataSync] == 'sync'`
   (`shell_project.dart:127`, `table_info.dart:153`).
3. Sync re-fetches by *replaying a creation script* stored in `metaParams['.script']`.
   `DataHistory` refuses to record one for processed calls — and `grok.data.files.openTable`
   runs `processed: true` (`grok_api.dart:992`, skipped at `shell.dart:1037,1120`). A
   file-opened table therefore has **no creation script at all**, so there is nothing to sync.
4. For query results, `data_history.dart:48` is explicit:
   `if (r.func.isDirty || (r.func is DataQuery && !r.func.isOnServer)) return;` — **an unsaved
   or dirty query produces no creation script**. The publish dialog even *hides* the data-sync
   switch when no script exists (`project_entity_move.dart:341,496`). That is the answer to the
   user's third report: saving the query server-side first is a hard prerequisite, and the
   dialog additionally links the query **and its connection** into the project
   (`project_entity_move.dart:378-399`) so a share is usable by anyone else.

**Why Grokky got it wrong.** [`plugin/skills/datagrok-projects/SKILL.md`](../dockerfiles/claude-runtime/plugin/skills/datagrok-projects/SKILL.md)
is the model's only teaching source for project saves. Read in full: the words *sync*,
`.script`, `metaParams`, and `showSaveDialog` **do not appear anywhere in it**. Asked for sync,
the model improvised — and improvised the only thing the API surface visibly offers.

<a id="f-13"></a>
**F-13 · CRITICAL · the skill's save recipe destroys existing data-sync configuration.**
Both recipes in the skill do `uploadDataFrame(t)` then `tables.save(t.getTableInfo())`. The
`TableInfo` is fresh, so its `metaParams` are empty; `metaParams` has no `ignoreForJson`
(`grok_shared.g.dart:2009-2012`), so **the empty map is serialized and sent**.

The server-side mechanism, read in full (`repository_meta_params_mixin.dart:44-57`) — the
precise behaviour matters, because a casual reading of `params.addAll(allParams)` suggests
existing rows are preserved, and for the rows that matter here they are not:

```dart
var params = m.entityMetaParams.toList();          // derived from metaParams — EMPTY for a fresh TableInfo
var allParams = await db.metaParams.where(...);    // all existing rows for this entity
await getForeignMetaParams(allParams);             // REMOVES rows owned by the caller's own groups
params.addAll(allParams);                          // only FOREIGN-owned rows are carried over
await db.sql('delete from meta_params where entity_id = @eid');
for (var t in params) await db.metaParams.save(t); // reinsert: (arrived ∪ foreign)
```

`entityMetaParams` is a derived getter over the `metaParams` map (`mixins.dart:106-111`), so an
empty map yields an empty list. `getForeignMetaParams` (`:29-35`) strips every row whose owner
is in the caller's group hierarchy. **So the sync rows a user (or their group) previously wrote —
`.script`, `.data-sync`, `.VariableName` — are deleted and not restored.** Rows owned by a group
the caller does not belong to survive. It happens twice per save, since `uploadDataFrame`
internally saves another empty `TableInfo` (`tables_client.dart:84`; `saveInfo` defaults true and
js-api exposes no way to pass false).

Core's own `Project.upload` does the opposite: it saves the live `TableInfo` *with* its
`metaParams` and skips the binary upload entirely for synced tables (`project.dart:232-239`).

> **Say "save my project" on a data-synced dashboard you own, and its sync configuration is
> silently and unrecoverably destroyed.** This is the single most serious finding in this audit.

*Core-side observation while verifying this:* `repository_meta_params_mixin.dart:49` reads
`params.removeWhere((t) => allParams.contains((a) => a.id == t.id))` — `List.contains` is being
passed a closure, which can never equal an element, so the guard is a permanent no-op and
same-named arriving/foreign params can be inserted twice. Unrelated to Grokky, worth a ticket.

**Fixes, in order.**

1. **Rewrite the skill.** Interactive path: `DG.Project.showSaveDialog({tables, views, name, project})`
   — the platform's purpose-built entry, which already does per-table sync toggles, dependency
   linking and upload ([js-api/src/entities/project.ts:49-58](../../../js-api/src/entities/project.ts)).
   Headless path: rehydrate `metaParams` from the server before saving, use `'sync'` not `'true'`,
   never `uploadDataFrame` a synced table, and save the `TableInfo` **last**.
2. **Teach the prerequisite:** before promising sync for query results, assert
   `q.isOnServer && !q.isDirty`; if not, save the query and re-run it so `DataHistory` writes
   `.script`; then link the query *and its connection* into the project.
3. **Platform:** expose `Project.upload()` to JS, add `saveInfo` to `uploadDataFrame`, make
   `TableInfo.fromTable` carry persistable tag values, and add `TableInfo.enableDataSync()`
   that validates the preconditions and throws typed errors. See [§7](#7-what-the-platform-does-not-give-grokky).
4. **Verification rule:** a claim about *persisted* state must be proven by a `grok.dapi.*`
   re-read, never from `t`/`view`/`grok.shell`. See [§5.2](#52-not-verified-on-a-flawless-action).

### 5.2 "Not verified" on a flawless action

**The user's report.** Three viewers added correctly; the exec block's own return value proved
four viewers existed; the panel still showed *"Not verified — the assistant could not confirm
this action took effect."*

**Root cause: three defects that were fixed in source on 2026-07-31 (commit `71eee21d1a`).**
Verified by reading the diff:

- `runVerification` called `executeSingleBlock(assertion)` **with no wrapper**. A bare
  expression like `Array.from(view.viewers).length >= 4` inside `return (async () => { … })()`
  evaluates to `undefined`, so `passed:false` with `error:null` — a correct assertion reported
  as a failed one.
- The block message read *"the action did NOT take effect as claimed"* — the gate told the
  model its correct action had failed, which is exactly the confusion visible in the user's
  transcript.
- The self-verify branch did not reset `pendingActions`.

**So the primary action is deployment, not code.** The container compiles its own source
inside the image and `grok publish` does not rebuild it. **Any `grokky-claude-runtime` image
built before 2026-07-31 still reproduces this exactly.**

<a id="f-02"></a>
**F-02 · MEDIUM · split-brain deployment with no version handshake.** Half the fix lives in
the image (`verify.ts`), half in the webpack bundle (`exec-blocks.ts`), and the WebSocket
protocol carries no build id in either direction ([types.ts:52-126](../dockerfiles/claude-runtime/src/types.ts),
[runtime-client.ts:111-152](../src/claude/runtime-client.ts)). Neither side can detect that the
other is stale. **Fix:** emit a commit/build id in the connect handshake or `sync_status` and
warn on mismatch.

**Live residual defects in the same failure class** — each can still turn a correct action
into "Not verified":

<a id="f-03"></a>
- **F-03 · MEDIUM · `wrapAssertion`'s `\breturn\b` regex is token-blind**
  ([exec-blocks.ts:40-48](../src/claude/exec-blocks.ts)). An assertion whose only `return` is
  inside a callback — `…filter(v => { return v.type === DG.VIEWER.SCATTER_PLOT; }).length >= 1` —
  short-circuits the wrapper, yields `undefined`, and reports failure. Same for `return` inside
  a string. **Fix:** prefer the parse test (`new Function('return (' + a + '\n)')`) and fall
  back to raw text only when it fails to parse.
<a id="f-04"></a>
- **F-04 · MEDIUM · a non-serializable result inverts a passing verdict**
  ([runtime-client.ts:215-227](../src/claude/runtime-client.ts)). If `observed` or `returnValue`
  contains a cyclic Dart handle — e.g. returning `Array.from(view.viewers)` — the catch replaces
  the **entire** response with `{success:false, passed:false}`. A true pass becomes a failure.
  `serializeResult` already exists ([view-tools.ts:184](../src/ai/view-tools.ts)) but is never
  applied on the exec/verify path. **Fix:** serialize before responding; degrade only the
  offending field.
<a id="f-05"></a>
- **F-05 · LOW · a legitimately falsy observation can never pass**
  ([exec-blocks.ts:67](../src/claude/exec-blocks.ts)): `passed: res.error == null && !!res.value`.
  "Close all charts" observing `0` remaining is unverifiable by construction.
<a id="f-06"></a>
- **F-06 · MEDIUM · the gate is satisfiable by `assertion: 'return true'`**
  ([verify.ts:81-86](../dockerfiles/claude-runtime/src/verify.ts)) — which clears all pending
  actions and resets both counters. The only defence is prose in the tool schema. This is most
  likely to be exercised precisely when the model is under block pressure.
<a id="f-07"></a>
- **F-07 · MEDIUM · `get_view_function_result` mutates without arming the gate.** Both view
  invocation tools share one unrestricted runner ([view-tools.ts:319-320](../src/ai/view-tools.ts)),
  and the verifier classifies read-only by *name prefix* (`/^(whoami$|list|get|search|read|
  download|find)/`, [verify.ts:5](../dockerfiles/claude-runtime/src/verify.ts)) — so `get_…`
  matches, and a state-changing `DG.Func` invoked through it mutates the workspace with no
  proof demanded and no `unverified` flag.
<a id="f-08"></a>
- **F-08 · LOW · persistence claims are verified against client memory.** The block message
  says *"RE-READS all affected state from `t`/`view`/`grok`"*. `grok` technically includes
  `grok.dapi`, but nothing requires it for claims about *saved* state — which is exactly how
  failure 5.1 "verified" itself.

**The structural answer** is in [§8.2](#82-verification-that-does-not-depend-on-the-model).

### 5.3 "Save query results as a data-synced project" — impossible, and Grokky didn't know

## 6. Findings

Ordered by theme. `F-01`…`F-45` are the verified set; each was re-checked against source.

### 6.1 Execution and trust

<a id="f-09"></a>
**F-09 · HIGH · model-authored JavaScript executes with the page's full authority, with no
consent step.** [ui.ts:525-531](../src/ai/ui.ts) → [exec-blocks.ts:17-20](../src/claude/exec-blocks.ts):
`new Function('grok','ui','DG','view','t', 'return (async () => {'+code+'})()')`. It also closes
over `window`, `document`, `fetch`, `localStorage`, and reaches `grok.dapi.token`. The panel
**already ships a confirmation mechanism** (`addConfirmMessage`, [panel.ts:487-514,551](../src/ai/panel.ts)) —
its only call sites are commented out in the non-bundled `src/depr/`. Combined with `WebSearch`/
`WebFetch` in `allowedTools`, all three legs of the "lethal trifecta" are present and unmitigated:
private data, untrusted content, exfiltration capability.
**Fix:** risk-tiered consent (auto-run reads and additive UI changes; confirm the destructive
class), plus the compensating controls in [§8.3](#83-a-trust-model-that-does-not-break-the-product).

<a id="f-01"></a>
**F-01 · HIGH · assistant markdown is rendered with a trusting sanitizer, and no CSP exists.**
[panel.ts:687](../src/ai/panel.ts) and [utils.ts:266](../src/utils.ts) call `ui.markdown` →

executes in the user's authenticated tab, and re-executes every time the stored conversation is
reopened. **Fix in the platform, not the plugin:** an untrusted mode on `ui.markdown` fixes

<a id="f-10"></a>
**F-10 · MEDIUM · typing in the search box runs generated JavaScript.**

<a id="f-11"></a>
**F-11 · MEDIUM · exec return values are injected into model context uncapped.**

### 6.2 The container: multi-tenancy and lifecycle

One `grokky-claude-runtime` instance, 1 CPU, serves the entire deployment. Every turn runs as
uid 1001 `grok`.

<a id="f-15"></a>
**F-15 · HIGH · per-user identity comes from an unverified JWT.**
[user-dir.ts:8-25](../dockerfiles/claude-runtime/src/user/user-dir.ts) base64-decodes the token
payload and uses `payload.sub` as a path segment with **no signature check and no character
validation**. Any client that can reach `/ws` can present a hand-crafted unsigned token and get
`cwd=/users/<victim>` with read tools enabled; an unsanitized `sub` also escapes `/users` by
traversal. **Fix:** resolve identity once per connection via an authenticated
`GET /public/v1/users/current` and validate against `/^[A-Za-z0-9_.-]+$/`.

<a id="f-16"></a>
**F-16 · HIGH · cross-user private files are readable.** Each user's synced Home files live at
`/users/<login>/agents` mode 644, owned by the same uid every turn runs as. The only PreToolUse
guard blocks `/workspace` — not `/users` ([query-options.ts:15-31](../dockerfiles/claude-runtime/src/query-options.ts)),
and in fact explicitly whitelists `/users/<anyone>/workspace` before testing. `Read /users/<other>/agents/…`
succeeds.

<a id="f-17"></a>
**F-17 · HIGH · provider credentials sit inside the agent's blast radius.** `allowedTools`
includes `Bash`, `WebFetch`, `Write`; `permissionMode: 'acceptEdits'`; no `sandbox`, no `env`
scoping, and `canUseTool` ([session.ts:306-312](../dockerfiles/claude-runtime/src/session.ts))
returns `{behavior: 'allow'}` for **every tool and every input**, making the SDK's permission
ladder a no-op. `process.env` still holds the provider credentials under both the SDK names and
the raw injected names, and `~/.claude/.credentials.json` is on disk. Bash + WebFetch + that env
is a complete exfiltration primitive.

<a id="f-18"></a>
**F-18 · HIGH · watchdog and reaper are container-wide and identity-blind.**
`killStrayChildren` ([watchdog.ts:59-68](../dockerfiles/claude-runtime/src/watchdog.ts)) SIGKILLs
**every** direct child when *one* session goes silent for 90 s — including other users' healthy
in-flight turns. The reaper's oldest-first arithmetic is unsound under concurrency: with two
live turns and one orphan, it kills the oldest live turn and the orphan survives.

### 6.8 Testing, CI, and product gaps

- **Zero tests.** `src/package-test.ts` exports an empty `tests` map, and `package.json` has no

- **Benchmark statistics are censored.** A timed-out rep is dropped from **both** the latency
  medians and the accuracy denominator ([benchmark.ts:389-405](../src/ai/benchmark/benchmark.ts)) —
  so an arm that times out more often reports a *lower* median and *higher* accuracy (2 timeouts

- **Feedback is a placebo.** Thumbs up/down render and toast "Thanks for your feedback!"; the

- **Keyboard-inaccessible.** Every control (Send/Stop, New Chat, History, Copy, Mic, Wand,

- **No admin documentation.** `README.md` is one sentence; the help page has no setup section;

## 8. Measured against best practice

29 practices researched across Anthropic engineering and SDK docs, the MCP specification, OWASP
LLM Top 10, and comparable products (Databricks Assistant/Genie, Hex Magic, Deepnote, Jupyter
AI, VS Code Copilot Chat, Cursor). Sources in [Appendix B](#appendix-b--sources).

### 8.1 Where Grokky already leads

| Practice | Grokky |
|---|---|
| Small consolidated tool surface (<20) | 5 domain tools + 4 meta-tools + 3 browser tools ≈ 22, with the collapse **measured** in-repo |
| Byte-stable defs for prompt caching | `VIEW_TOOL_DEFS` is a module const; per-view functions never enter the tool list. Exemplary |
| Progressive disclosure / search-then-load | two layers: `list_view_functions` (≤10 ranked briefs) and op-less MCP calls returning the domain schema |
| Token-efficient tool responses | compact JSON, paging, 20k cap, *corrective* truncation messages — with the reasoning documented in the file header |
| Errors that enable self-correction | unknown-op errors list the available ops; missing params return the catalog. Near-exemplary |
| Skills as files with routing frontmatter | 12 skills as a local plugin, attached only for full-prompt turns, two inlined for byte stability |
| Poka-yoke argument design | the `view` parameter is injected at call time and hidden from the model entirely |
| Eval harness | drives the real pipeline; TTFT/cost/tool-order/unverified-rate; deterministic asserts + majority-vote judge |
| Act→verify gating | **ahead of every product surveyed** — no comparable product blocks turn-end on unverified actions |

### 8.2 Where it lags: verification that does not depend on the model

Both reported failures come from the same root: the observer is the same model, in the same
substrate, as the actor. Anthropic's framing is that agents need *"ground truth from the
environment at each step"*. The fix is a **ledger**, not a better assertion.

- **Layer 0 — observation ledger (browser, zero model cooperation).** `executeSingleBlock`
  already owns the moment around the action. Subscribe before, unsubscribe after, and return a
  receipt. Everything needed already exists: `grok.functions.onBeforeRunAction`/`onAfterRunAction`
  (a complete receipt for any registered function), `onViewerAdded`/`onViewAdded`/`onTableAdded`/
  `onProjectSaved`/`onQueryFinished`/`onDialogShown`, `DataFrame.onDataChanged`/`onRowsFiltered`/
  `onSelectionChanged`, plus a cheap pre/post snapshot of `rowCount`, column names, `filter.trueCount`,
  viewer types.
- **Layer 1 — declared effect instead of authored assertion.** Change the exec contract from
  "write JS returning something truthy" to "declare what you expect to change":
  `{effect: 'viewer_added'|'column_added'|'rows_filtered'|'project_saved'|…, expect: {…}}`. The
  harness matches the declaration against the ledger. **Failure 5.2 disappears** — four
  `onViewerAdded` events are observed regardless of `return` statements — and so does the
  "truthy = verified" contradiction that makes an observed `0` unverifiable.
- **Layer 2 — server truth for persistence claims.** Any effect in the persistence class must be
  confirmed by an **independent re-read the harness performs**: `grok.dapi.tables.find(id)` and
  assert `metaParams['.data-sync'] === 'sync'`. **Failure 5.1 disappears.**
- **Layer 3 — LLM assertions**, retained only for effects the ledger cannot see, with F-03…F-06
  fixed.
- **Make receipts visible.** `verify.description` and `observed` are computed on every action and
  thrown away; only the red banner renders. One line per action — *"Added scatter plot · observed
  4 viewers · verified"*, code collapsed — matches Copilot's `pastTenseMessage` and Genie's
  trusted-asset labeling, and lets a user catch a wrong action before it compounds.

One mechanism, four payoffs: the ledger is the verification signal, the audit record, the undo
instruction, and the benchmark ground truth.

### 8.3 A trust model that does not break the product

Real sandboxing is off the table on merit: the product's value **is** mutating the live
`grok.shell.v`, which a Worker cannot reach, and an iframe with `allow-scripts` +
`allow-same-origin` is equivalent to no sandbox. ShadowRealm is Stage 2.7; the Chrome 50 floor
rules out SES. So: layered compensating controls, ordered by risk removed per unit of product
value lost.

1. **A platform CSP with a `connect-src` allowlist.** None exists anywhere in core today. This
   is the highest-leverage control in the entire review — it severs the exfiltration leg of the
   lethal trifecta for *all* executed code without removing a single feature, and blunts F-01 at
   the same time.
2. **Sanitizing renderer for untrusted content** (F-01) — in js-api, so every plugin benefits.
3. **Verified container identity, per-user path deny, SSRF allowlist, real `canUseTool`**
   (F-15, F-16, F-17, F-44).
4. **Facade + preflight on exec** — ten lines: declare `fetch`, `XMLHttpRequest`, `WebSocket`,
   `localStorage`, `eval`, `Function` as extra parameter names bound to throwing stubs, and
   statically reject bodies mentioning `dapi.token` or `import(`. Not a sandbox — a speed bump
   that removes the cheapest primitives and, more valuably, *produces a signal when tripped*.
5. **Risk-tiered consent, not a blanket gate.** Auto-run reads and additive UI changes; require
   Run/Cancel for deletes, file writes, permission changes, and container `Bash`. The confirm UI
   already exists and is unused. Add a per-session autonomy dial, as Deepnote and Databricks ship.
6. **Make the search-bar Execute provider preview-only** (F-10).
7. **Server-side audit** of every exec body, tool call, and verdict, keyed to the *verified* user
   id. The `input_request`/`input_response` pair is a single chokepoint both directions already
   traverse.
8. **Taint-track the turn**: once WebFetch/WebSearch/synced-file/DB text enters context, drop
   WebFetch and force confirmation on exec for the remainder.
9. **Tell the truth in `CLAUDE.md:19-21`.** An honest threat model — trusted-user enterprise
   install; model code runs with the user's full session authority — is defensible. The current
   wording causes reviewers to skip diligence they would otherwise do.

### 8.4 Where knowledge should live

Grokky has six knowledge homes and no ownership rule. **The rule to adopt: knowledge that
describes a capability belongs to the capability, not to the assistant.**

- Function semantics → `DG.Func` metadata (`description`, `friendlyName`, `helpUrl`, per-input
  `Property.description`), owned by the package author, versioned with the code, already surfaced
  by `list_view_functions`. `funcBrief` should additionally emit required-vs-optional and
  `helpUrl` — today the model cannot tell which parameters it must supply.
- Widget/view semantics → `aiDescription` + `getFunctions()`.
- DB schema semantics → sticky meta, generated by an admin action. Every comparable product
  harvests from the governed metadata store; Grokky ships the anti-pattern (F-47) while owning
  the correct pipeline.
- Product behavior → help docs, indexed. Already correct.
- Skills → **only** cross-cutting judgment no single function owns: routing, footguns,
  when-not-to. **Every skill section that is a code recipe is a missing platform function** —
  delete it as that function lands. Skill byte-count is a debt metric, not an asset.
- System prompt → invariants only, byte-stable. Already correct.

### 8.5 Other gaps against comparables

| Practice | Product precedent | Grokky |
|---|---|---|
| Tool annotations (`readOnlyHint`) | MCP spec, Agent SDK | **absent everywhere** — no `sdkTool` or `server.tool` call passes annotations, so read-only tools cannot be parallelized and mutation semantics are undeclared |
| Undo / checkpoints | Cursor snapshots each agent turn | none; `verify.ts:132-133` instructs the model *around* irreversibility instead of solving it. Cheapest win: snapshot `view.saveLayout()` + filters before each exec, offer "Revert this turn" |
| Visible plan / step list | Databricks Planner, Copilot | `tool_activity` is shown one line at a time and discarded; `TodoWrite`/`Task` are deliberately excluded. Accumulating the events into a collapsible "Steps" list is rendering-only work |
| Durable server-side sessions | Agent SDK writes every session to disk | in-memory LRU(200); the SDK's own JSONL is never re-listed (F-43) |
| Committed eval baseline in CI | Copilot's `stest` runs each scenario 10× | harness exists, runs manually in a browser, no committed baseline, unpinned CLI |
| Cost control in dollars | SDK `max_budget_usd`, `maxTurns` | neither is passed; quota is a client-side counter hardcoded to 1000 |
| Feedback loop | GitHub treats feedback as eval input | `receiveFeedback` is an empty function |
| Versioned protocol | Jupyter AI moved to ACP | bespoke WS protocol documented as prose, no version field (F-02). *Not* a recommendation to adopt ACP — the verify/grounding gates justify the custom runtime — but the contract should be schema'd and versioned |
