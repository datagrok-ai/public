Artifact Alignment & Discoverability

Making Datagrok artifacts (dashboards, queries, model runs) discoverable by aligning them with drug-program structure — delivered as a JS plugin.

The idea

Publishing an artifact feels like saving a document to the program's shared place — and it doubles as distribution: the published artifact is automatically visible to the program's audience, replacing manual sharing with N colleagues. Discovery then means one server-side query: "everything approved for program Alpha / molecule GRK-1234 / study ABC-301".

Re-publishing under the same key appends a new version row (it starts unapproved by server default); the previous approved version stays live and discoverable until the replacement is approved, and only then retires into a separate, non-discoverable history table — see the Schema tab.

Principles

  • Single source of truth. A package-managed domain schema holds identity, relationships, and curation state. Anything owned by another system (program stage, status, indication) is display-only informational state — never governed here.
  • Latest-approved primary table, append-only history. Each publication has a durable publication_id; among live rows, at most one approved version and at most one in-review (pending/rejected) version exist per publication — the table's business key (publication_id, status), backed by a partial unique index over live rows and enforced on insert AND update (a status flip into an occupied slot fails with a typed error), plus the service invariant that at most one non-approved row is live. Discovery reads approved rows only, so it still sees exactly one row per publication. Re-publish appends a new pending row alongside the live approved one; the old version is archived only when its replacement is approved. Versions never share a row, so approval can never leak across versions.
  • Immutability by ownership (target state) — each published version is a frozen copy, stamped and excluded from the author's personal history. Once the platform gains per-run access control and ownership transfer (see Core tasks), the copy becomes service-owned and view-only for everyone including the author; until then it remains author-owned. Data-sync dashboards freeze the definition; data refreshes at open with the opener's rights.
  • Review gate is configuration, not architecture. Global default off + a gated artifact-type list (e.g. model runs, reviewed by an SME — a real role). Ungated publications are auto-approved instantly; the schema is identical in both modes. Approval = endorsement badge that pins content (the copy is frozen).
  • No deprecation by design. Old and killed-program artifacts are the reuse value; history versions stay accessible, just out of discovery.

What discovery can answer

  • Everything for a program / study / workstream / molecule, in any combination, with approval status — one server-side faceted query (incl. M:N molecule paths: compounds.registration_code = "GRK-1234").
  • Cross-program molecule queries, set questions (compounds.id = null), rollup counts, shareable saved filters, parameterized dashboards with URL deep links.
  • Counts and facets are correct by construction — discovery reads only approved rows, and at most one approved row exists per publication, so no consumer needs to filter out old versions.

Known limits: text/content search and structure-based chemistry are out (bridgeable via chemistry tooling: structure → registration codes); only published artifacts are discoverable.

Value proposition

"Where is the PK dashboard for study ABC-201?" is a daily question in every program team. The catalog answers it — and unlike document indexes (SharePoint, Confluence) its entries are live, executable, data-connected artifacts. The publisher's own incentive is built in: publishing is distribution — publish once and the right audience sees it, instead of manually sharing with N colleagues.

Adoption model

  • Default is instant gratification: gate off → publish is immediately discoverable and audience-shared. No approval latency, no bottleneck; the file-share mental model — including re-saving under the same name, which just creates the next version.
  • Quality without gates: provenance (author, date, program, study on every hit) plus endorsement — an asynchronous SME badge that upgrades ranking. Junk sinks instead of blocking. Frozen copies mean the badge can never bless content the SME didn't see, and a new version always starts unendorsed.
  • The gate where it's real: SME review of model runs is an actual, named role in pharma (model validation culture). Gate selected artifact types; leave dashboards/queries ungated. Note the versioning behavior: an update to a gated artifact also goes through review, but while it is pending the publication keeps serving its last approved version — the update shows as "in re-review" alongside it, visible to the author and approvers only. A rejected update never changes what the audience sees; the previous version retires only when its replacement is approved.
  • Cold start: bulk-publish tooling for the existing artifact corpus, and master-data sync for the program/compound/study registry (required in large organizations — a hand-maintained registry drifts; small organizations keep the manual admin path on the same model).
  • Reuse is the payoff: publications are never deprecated; killed-program artifacts remain discoverable — "we saw this signal in program X three years ago" is the classic high-value reuse. Search always returns the latest approved version only; earlier versions stay accessible from the publication's history, never cluttering results.

Compliance posture

A discovery catalog with optional curation — not a GxP system of record. Endorsement is a curation signal, not an electronic signature; regulated decisions belong in the customer's validated systems. Several review-workflow requirements are inherent in the design and are therefore not gaps: content pinning and change-triggered re-review (frozen copies; a republished version resets to unapproved while the audience keeps seeing the last approved version until the new one passes), the rejection → resubmission loop (resubmit = the next version through the normal flow, with the rejected version and its reason archived), and reviewer delegation (approvers-group membership). What remains missing is listed below.

Publish & republish flow (catalog service, runs as the publishing user)

  1. Freeze the author's run → new frozen copy: a stamped meta call saved through the same path as personal history. Workflow runs share the source's step calls and dataframes; function runs re-upload their dataframes with a View grant to the program viewers group. (Service ownership of the copy awaits core per-run ACL — see Core tasks.)
  2. First publish: mint publication_id, insert the version-1 row. Republish (same (program, study, name) → same publication_id): insert the new row with revision + 1 alongside the live approved row; if an older in-review row is still live (a rejected or superseded draft), archive it to alignment_history first. Curation values (tags, path) are copied forward from the latest version.
  3. The new row's status lands 'pending' by server default — approval can never carry over between versions because versions never share a row. The previous approved version stays live and discoverable while the new one is in review; a rejection leaves it untouched.
  4. Approval (by an approver, or by the service in the same breath when the gate is off for the artifact's type — same audit trail): copy the previously approved row into alignment_history, soft-delete it, and set the new row to approved — one domains transaction. The auto-approval runs as the acting user, so it succeeds only when they hold approval rights; otherwise the version stays pending for a real approver. Gated ⇒ notify the approvers group explicitly at publish time.

The multi-row steps (archive + insert on republish, archive + flip on approval) run as one domains transaction (grok.dapi.domains.transaction), so no partial-failure window exists and a publication never briefly lacks its approved row. The business-key guards back it: a duplicate insert against the live-row business key fails with a typed unique-violation error, and so does an update that would create a second approved live row (the flip guard); re-inserting after the soft-delete succeeds; a duplicate history insert against the (publication_id, revision) business key is a graceful no-op (created: false, status: 'duplicate'). What the server still cannot guarantee is referential: version rows point at frozen artifact FuncCalls with no FK/onDelete semantics, so a deleted artifact can only be caught by a periodic referential scan — planned service work, not in the PoC (see Core tasks).

Permissions (as implemented)

  • Umbrella groups — three schema-wide groups (Artifacts: Viewers / Contributors / Approvers) hold the table-level grants: all three get View on the catalog tables, contributors and approvers additionally get Edit, plus Delete on program — the securing entity for the master chain, which is what authorizes the archive's row delete (verified: a Delete grant on the alignment table itself does not reach rows). The compound and tag registries are View for all users (and Edit for contributors — publish creates missing entries by name).
  • Per-program groups — each program gets its own viewers / contributors / approvers groups, nested into the matching umbrellas; the program row is shared View to its viewers and Edit to its contributors and approvers. Because the table gate is umbrella-wide, any program's audience sees the whole registry; per-row trimming is a core ask. Tiers are cumulative by convention: an approver must also be a member of the program's contributors and viewers groups (and a contributor of the viewers group) — the curation column grants sit on the contributors umbrella, so an approver outside it would pass the service checks yet fail the column write. Membership provisioning must assign the lower tiers along with the role.
  • Column security on alignment — the approval columns (status, approved_by, approved_on, reject_reason) are View for everyone and Edit for the approvers umbrella only; the curation column (path) is Edit for the contributors umbrella. A non-approver writing status gets a typed denial.
  • Service-side guards — publish and curation require transitive membership in the target program's contributors or approvers group; approve/reject require approvers-group membership and reviewer ≠ author; the auto-approve on publish runs as the acting user, so column security decides whether it sticks.
  • Frozen data — the dataframes a function-run freeze uploads are granted View to the program viewers group only. Workflow freezes share the source run's dataframes instead, which keep their personal-history default grants — see Known design gaps.
  • Restricted scopes — audiences are exact per-artifact grants. Blinded-study metadata: publish-on-unblind by default (version rows delegate to the program, so their existence is visible to program viewers).

Known design gaps

  • Registry-wide write authority — domain writes are authorized at table level, so any contributors/approvers-umbrella member can write rows of any program via raw REST; the per-program guard is service-side and bypassable. This includes deletes: archiving requires Delete, which is authorized against the securing entity (the program table), so the writer umbrellas hold table-wide Delete there — via raw REST that reaches every program-secured row, including studies and the alignment_history archive, whose append-only property is therefore service-side convention. Blocked on Core tasks: row-scoped write authorization.
  • Frozen copies are neither audience-gated nor immutable — a run is loadable by id by anyone and stays the author's to edit or delete; only its dataframes carry audience grants. Blocked on Core tasks: FuncCall as a full entity.
  • Workflow-run data is not audience-gated — a workflow freeze shares the source run's step calls and dataframes (no re-upload), so those dataframes keep their personal-history default grant and are readable by any user who learns their id; only function-run freezes re-upload with viewers-only grants. A plugin-side fix (copy or re-grant the step dataframes at publish) trades away the shared-steps design; pinned by a canary test until scoped.

Service responsibilities (beyond the publish flow)

  • Group provisioning per program; batch audience backfills when a program's groups change.
  • Drift check (planned; not in the PoC): a referential scan for version rows whose frozen artifact no longer resolves (FuncCall references carry no FK semantics — see Core tasks), intended (registry) vs. actual (entity ACL) grant reconciliation, and audit-trail scans for writes by non-members and for approvals set outside the approvers group.
  • Exclude version rows whose frozen copy was admin-deleted; scheduled registry export.
  • Per-type freeze mechanics: queries/scripts are content strings (trivial); projects/dashboards via the platform clone; workflow/model runs re-save through the same save path as personal history — a stamped meta call over the same serialized config, sharing step calls and dataframes with the source run (no deep clone), and still runnable.
  • Grant reconciliation is post-hoc by platform necessity (no cancellable pre-commit hooks exist) — retries required; grants sit outside the domains transaction, so partial failures remain possible there and are repairable.

Storage & ops

Domain tables live in the main platform Postgres. Non-Postgres surfaces needing backup: platform file storage — domain file uploads and published dataframe blobs. No documented on-prem backup procedure exists today (cloud file-storage backup is documented); this is an explicit ops prerequisite for production.

Platform (core) tasks

Asks on the Datagrok core, separate from plugin work. Grouped by how hard they block the design; each item names its type: bug improvement feature.

Blockers

  1. Entity dialog extension points (save / share / load). feature
    The platform's save and share dialogs cannot be extended by packages: there is no API to add a step or a field, and no cancellable pre-save/pre-share event — only post-hoc notifications. A cataloging plugin needs to inject a "publish to program" step into the dialogs users already go through, and a catalog picker into open/load. Until an extension point exists, publishing lives in a context-menu / Actions-pane action.
  2. FuncCall as a full entity: per-run ACL, ownership transfer, lock. feature
    A function run cannot be access-controlled: only the dataframes it uploads can be granted to an audience — the run itself is loadable by id by any user, and it remains the author's to edit or soft-delete. Rows that reference runs by id have no FK/onDelete semantics either, so deleting a run silently breaks whatever points at it. Needed: grant View on a run to a group, hand a run's ownership to a service identity, and lock a run against further writes. Without this, published snapshot copies are neither audience-gated nor immutable.
  3. Row-scoped write authorization on master-mode domain tables. feature
    Domain writes are authorized at table level: an Edit grant on a table allows inserting and updating rows that belong to any master row, while an Edit share on the delegate row alone authorizes nothing. Per-master isolation ("contributors of program A write only A's rows") must therefore be enforced by application services running in the caller's session, which a direct REST call bypasses. Needed: a declarative write predicate scoped through the delegate chain, or a server-side enforcement hook.

Important

  1. Working notification channel for domain table watch. bug
    Subscribing to a domain table's watch channel succeeds, but no notification reaches the watcher's feed when another user changes the table. Approver notifications and any review-queue SLA/escalation depend on this channel; until it works, services must send explicit notifications themselves.
  2. Manifest schema migrations are refused by one side and ignored by the other. bug
    The deploy tool refuses a column drop unless an explicit migration is declared, but the server ignores the manifest's migrations key entirely, and the expected migration syntax is not documented. Net effect: column drops are impossible (obsolete columns must stay declared forever) and renames degrade to drop+add. Needed before any breaking registry change: a migration path that is honored end-to-end and documented.
  3. Audit for domain permission changes. improvement
    A grant/revoke round-trip on a domain table produces no audit record at either the domain layer or the platform log; only classic entity shares are logged. Table stakes for regulated-adjacent customers.
  4. Server-side sub-entity handling for system-created FuncCalls. improvement
    Snapshot copies created by services land in the same run history as personal saves, cluttering every user's run listings with system-generated garbage; hiding them relies on every listing UI filtering on a call option client-side. A server-side sub-entity flag would hide them from all listings at the source.
  5. Per-table UI affordance control in domain views: create button, row click, context menu. improvement
    The automatic "New <singular>" row-create button cannot be suppressed through the manifest (revoking insert permission instead would break services that insert rows on the user's behalf) — and the same holds for the row's click/open behavior and its context menu: a JS handler may only ADD actions, never replace the platform's Edit/Delete/History commands or the row-open handler. Overriding is possible today only through the global onContextMenu hook, removing items by their label text — verified working, but off-contract and fragile across platform versions. Needed: manifest- or handler-level control over per-table create/edit affordances, the row click handler, and the platform context-menu items.

Normal

  1. FuncCall listing performance and API shape. improvement
    A filtered run-list request carries a fixed latency on the order of seconds even for small pages; there is no count endpoint and no bulk or criteria-based delete. History UIs that pull a function's full run list degrade with the function's lifetime run count — needs server-side newest-N paging, ordering, and counts.
  2. Typed JS API for property-schema grants. improvement
    Single-column security has a typed surface (restrict a column, grant View/Edit per group). Manifest-declared multi-column property schemas can only be granted through the raw REST route — a typed grant/revoke/list surface is missing.
  3. Declarative column immutability. feature
    An immutable manifest flag for columns that must never change after insert. Today immutability is application-layer convention plus after-the-fact audit inspection.
  4. Value-conditional column security. feature
    Transition rules such as "a status may not leave an approved state" or "the row's author may not write the approval columns" are inexpressible in the manifest; they can only be approximated by keeping whole roles off a column and re-checking in services.

Low

  1. Cold-boot readiness for domain views. bug
    Creating a domain view early in client startup (e.g. from a deep link) can crash grid construction with null errors while entity-type and property-schema metadata is still loading, leaving a dead grid that a refresh cannot revive. A JS app has no signal to await. Fix: the view awaits its own metadata dependencies, or the platform exposes an awaitable registry-ready signal. Downgraded 2026-08-21: after the plugin moved its handler registration off the boot path (autostart → init), the crash stopped reproducing across repeated cold deep links — fixed or sharply reduced in frequency; re-raise if it recurs.
  2. FuncCall re-wrapped incorrectly inside object-typed parameters. bug
    Passing a FuncCall across the function-call boundary inside an object-typed parameter delivers a wrongly re-wrapped value on the other side (shaped like a DataFrame wrapper, missing the call's properties); a funccall-typed parameter works. Fix the generic re-wrapping, or document object parameters as unsafe for entities.
  3. Documented backup & restore for on-prem deployments. improvement
    Domain tables live in the platform Postgres, but domain file uploads and published dataframes live in platform file storage; only cloud file-storage backup is documented. An on-prem restore runbook covering both stores is an ops prerequisite for production.
  4. Row-permission probes cannot reflect a request-level acting identity. improvement
    Row-permission answers are computed client-side and keyed to the session user. That is correct for normal sessions — administrators legitimately hold every permission, and restricted sessions report their real trimmed permissions — but a request-level impersonation token cannot change the answer, because the probe never reaches the server. Table-level capability probes (canInsert/canEdit) are per-request server calls and do honor the acting identity; row-permission probes need an equivalent server-truth path. Affects only code that emulates identities (headless tests, future service identities).
  5. Silent no-op delete on a version-scoped FuncCall miss. bug
    Deleting a function run through the default calls source resolves successfully while deleting nothing when the run belongs to another package version; only the all-package-versions source actually deletes it. A scoped miss should be an error, not a silent success. Low because runs are practically never deleted outside test tooling, and the FuncCall-as-entity work would rebuild deletion semantics anyway.
  6. Grants export / access-review reporting. feature
    Grants are listable per object only. A platform-level export of grants across all domain schemas, tables, and property schemas would provide the access-review evidence (who can see / edit / approve what) that security reviews ask for.
  7. Grant API parity for promoted domain rows. improvement
    Entity permission granting is binary View/Edit while Share/Delete are checkable but not grantable. The typed permissions API refuses promoted domain rows; the shares route accepts them but addresses groups by name only — and it also accepts non-grantable access levels (e.g. access=Delete) silently, reporting success with no authorizing effect. Promoted-row grants need a typed, id-addressed surface. The shares route is a workable interim.
