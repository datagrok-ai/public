Artifact Alignment & Discoverability

Making Datagrok artifacts (dashboards, queries, model runs) discoverable by aligning them with drug-program structure — delivered as a JS plugin. All mechanics marked ✅ were verified against a live Datagrok deployment (datagrok-api 1.27, August 2026), including permission-enforcement checks under restricted user accounts.

The idea

Publishing an artifact feels like saving a document to the program's shared place — and it doubles as distribution: the published artifact is automatically visible to the program's audience, replacing manual sharing with N colleagues. Discovery then means one server-side query: "everything approved for program Alpha / molecule GRK-1234 / study ABC-301".

Re-publishing under the same key appends a new version row (it starts unapproved by server default); the previous approved version stays live and discoverable until the replacement is approved, and only then retires into a separate, non-discoverable history table — see the Schema tab.

Principles

  • Single source of truth. A package-managed domain schema holds identity, relationships, and curation state. Anything owned by another system (program stage, status, indication) is display-only informational state — never governed here.
  • Latest-approved primary table, append-only history. Each publication has a durable publication_id; among live rows, at most one approved version and at most one in-review (pending/rejected) version exist per publication — the table's business key (publication_id, status), backed by a partial unique index over live rows and enforced on insert AND update ✅ verified (a status flip into an occupied slot fails with a typed error), plus the service invariant that at most one non-approved row is live. Discovery reads approved rows only, so it still sees exactly one row per publication. Re-publish appends a new pending row alongside the live approved one; the old version is archived only when its replacement is approved. Versions never share a row, so approval can never leak across versions.
  • Immutability by ownership ✅ verified — each published version is a frozen copy created by a catalog service identity; everyone (including the author) holds View and cannot modify or delete it. Data-sync dashboards freeze the definition; data refreshes at open with the opener's rights.
  • Review gate is configuration, not architecture. Global default off + a gated artifact-type list (e.g. model runs, reviewed by an SME — a real role). Ungated publications are auto-approved instantly; the schema is identical in both modes. Approval = endorsement badge that pins content (the copy is frozen).
  • No deprecation by design. Old and killed-program artifacts are the reuse value; history versions stay accessible, just out of discovery.

What discovery can answer

  • Everything for a program / study / workstream / molecule, in any combination, with approval status — one server-side faceted query ✅ (incl. M:N molecule paths: compounds.registration_code = "GRK-1234").
  • Cross-program molecule queries, set questions (compounds.id = null), rollup counts, shareable saved filters, parameterized dashboards with URL deep links.
  • Counts and facets are correct by construction — discovery reads only approved rows, and at most one approved row exists per publication, so no consumer needs to filter out old versions.

Known limits: text/content search and structure-based chemistry are out (bridgeable via chemistry tooling: structure → registration codes); only published artifacts are discoverable.

Value proposition

"Where is the PK dashboard for study ABC-201?" is a daily question in every program team. The catalog answers it — and unlike document indexes (SharePoint, Confluence) its entries are live, executable, data-connected artifacts. The publisher's own incentive is built in: publishing is distribution — publish once and the right audience sees it, instead of manually sharing with N colleagues.

Adoption model

  • Default is instant gratification: gate off → publish is immediately discoverable and audience-shared. No approval latency, no bottleneck; the file-share mental model — including re-saving under the same name, which just creates the next version.
  • Quality without gates: provenance (author, date, program, study on every hit) plus endorsement — an asynchronous SME badge that upgrades ranking. Junk sinks instead of blocking. Frozen copies mean the badge can never bless content the SME didn't see, and a new version always starts unendorsed.
  • The gate where it's real: SME review of model runs is an actual, named role in pharma (model validation culture). Gate selected artifact types; leave dashboards/queries ungated. Note the versioning behavior: an update to a gated artifact also goes through review, but while it is pending the publication keeps serving its last approved version — the update shows as "in re-review" alongside it, visible to the author and approvers only. A rejected update never changes what the audience sees; the previous version retires only when its replacement is approved.
  • Cold start: bulk-publish tooling for the existing artifact corpus, and master-data sync for the program/compound/study registry (required in large organizations — a hand-maintained registry drifts; small organizations keep the manual admin path on the same model).
  • Reuse is the payoff: publications are never deprecated; killed-program artifacts remain discoverable — "we saw this signal in program X three years ago" is the classic high-value reuse. Search always returns the latest approved version only; earlier versions stay accessible from the publication's history, never cluttering results.

Compliance posture

A discovery catalog with optional curation — not a GxP system of record. Endorsement is a curation signal, not an electronic signature; regulated decisions belong in the customer's validated systems. Several review-workflow requirements are inherent in the design and are therefore not gaps: content pinning and change-triggered re-review (frozen copies; a republished version resets to unapproved while the audience keeps seeing the last approved version until the new one passes), the rejection → resubmission loop (resubmit = the next version through the normal flow, with the rejected version and its reason archived), and reviewer delegation (approvers-group membership). What remains missing is listed below.

Publish & republish flow (catalog service, service identity)

  1. Clone the author's working copy → new frozen copy (service-owned; audience gets View).
  2. First publish: mint publication_id, insert the version-1 row. Republish (same (program, study, name) → same publication_id): insert the new row with revision + 1 alongside the live approved row; if an older in-review row is still live (a rejected or superseded draft), archive it to alignment_history first. Curation values (tags, path) are copied forward from the latest version.
  3. The new row's status lands 'pending' by server default — approval can never carry over between versions because versions never share a row. The previous approved version stays live and discoverable while the new one is in review; a rejection leaves it untouched.
  4. Approval (by an approver, or by the service in the same breath when the gate is off for the artifact's type — same audit trail): copy the previously approved row into alignment_history, soft-delete it, and set the new row to approved — one domains transaction. Gated ⇒ notify the approvers group explicitly at publish time.

The multi-row steps (archive + insert on republish, archive + flip on approval) run as one domains transaction (grok.dapi.domains.transaction), so no partial-failure window exists and a publication never briefly lacks its approved row. The business-key guards still back it — all verified: a duplicate insert against the live-row business key fails with a typed unique-violation error, and so does an update that would create a second approved live row (the flip guard); re-inserting after the soft-delete succeeds; a duplicate history insert against the (publication_id, revision) business key is a graceful no-op (created: false, status: 'duplicate'). What the server still cannot guarantee is referential: version rows point at frozen artifact FuncCalls with no FK/onDelete semantics, so the drift check reduces to a deep scan for artifacts that no longer resolve (see Core tasks).

Permissions

  • Viewers — View on each approved frozen copy (granted by the service) + alignment metadata visibility via the program delegate chain.
  • Contributors — may create version rows (see the write-coupling decision below), and hold Edit on the curation column group (tags, path) to organize published artifacts after the fact.
  • Approvers — Edit on the approval column group; only they can set status ✅ (typed denial for everyone else; authors cannot self-approve). View must be granted separately from Edit on a property schema ✅ — grant View broadly so everyone can filter on status.
  • Restricted scopes — audiences are exact per-artifact grants. Blinded-study metadata: publish-on-unblind by default (version rows delegate to the program, so their existence is visible to program viewers).

Known design gap: write coupling (accepted for v1)

Verified platform behavior: master mode routes writes through the delegate — inserting a version row requires Edit on the program row, so "can publish to Alpha" implies "can edit Alpha's registry row". v1 accepts this as the trivial path: contributors are granted Edit on the program table; registry edits by non-stewards are audited, detected by the drift check, and overwritten by master-data sync where one runs.

Marked as a design gap to be addressed — publishing rights should not expose the program registry row for editing.

Service responsibilities (beyond the publish flow)

  • Group provisioning per program; batch audience backfills when a program's groups change.
  • Drift check: intended (registry) vs. actual (entity ACL) grants; a deep referential scan for version rows whose frozen artifact no longer resolves (FuncCall references carry no FK semantics — see Core tasks); "approval only ever set by the approvers group or the service" scan over the audit trail.
  • Exclude version rows whose frozen copy was admin-deleted; scheduled registry export.
  • Per-type freeze mechanics: queries/scripts are content strings (trivial); projects/dashboards via the platform clone; workflow/model runs re-save through the same save path as personal history — a stamped meta call over the same serialized config, sharing step calls and dataframes with the source run (no deep clone), and still runnable.
  • Grant reconciliation is post-hoc by platform necessity (no cancellable pre-commit hooks exist) — retries required; grants sit outside the domains transaction, so partial failures remain possible there and are repairable.

Storage & ops

Domain tables live in the main platform Postgres. Non-Postgres surfaces needing backup: platform file storage — domain file uploads and published dataframe blobs. No documented on-prem backup procedure exists today (cloud file-storage backup is documented); this is an explicit ops prerequisite for production.

Entity dialog overrides — save / share / load

  • Save/share: inject a "publish to program" step — program pre-filled from context, optional study / compounds (auto-suggested from the artifact's data via semantic types) / workstream, and Name — pre-filled from the working copy. The republish key is (program, study, name): a match publishes the next version of that publication; a different name — or the same name under a different program or study — creates a new publication (exactly the file-save-dialog semantic). Requires a core dialog-extension point (the platform share dialog is closed to packages — verified); until it lands, the same dialog ships as a context-menu / Actions-pane action.

End-user filtering, no code required

The shipped domain UI provides: gallery views with a search bar (plain text or condition grammar), an auto-built filter panel (checkbox facets with live row counts that respect row-level access, histograms, date ranges), related filters following references up to three hops, an auto-generated facet per M:N relation (molecules as checkboxes), and saved filter presets that are shareable entities. "Open in Table View" turns any filtered subset into a full analytical table, recorded as a re-runnable query that respects the opener's permissions.

Platform (core) tasks

Asks on the Datagrok core, separate from plugin work. Each is backed by live verification, not speculation.

Blockers

  1. Entity dialog extension points (save / share / load). The share dialog is closed to packages (verified: no API, no cancellable pre-save/share event — only post-hoc share notifications). Needed for the publish step to live where users already are; a hard blocker for the ideal UX. Interim: context-menu / Actions-pane action.
  2. FuncCall as a full entity: per-run ACL, ownership transfer, lock. Verified: only a run's uploaded dataframes can be audience-scoped — the run itself stays loadable by id by everyone, and remains the author's to edit or soft-delete, so frozen run artifacts are neither audience-gated nor immutable; and catalog rows reference FuncCalls with no FK/onDelete semantics, so an author can delete shared step runs out from under a published artifact. Needed: grant View on a run to a group, hand ownership to a program/service identity, lock a run after approval. Placeholder calls sit commented in historyUtils.saveRun.

Important

  1. Typed JS API for property-schema grants. Per-column schemas do have a typed surface — shareColumn(column, group, permission) restricts a column and grants View/Edit per group (verified; the shape this design's approval/curation columns use). Manifest-declared (multi-column) property schemas still have only the REST route — grant/revoke/list is missing.
  2. Audit domain grant/revoke. Verified: a grant+revoke round-trip adds zero audit entries at both the domain layer and the platform log. Table stakes for regulated-adjacent customers.
  3. Working notification channel for domain table watch. Subscription confirms but nothing observable arrives in the user notification feed after another user's change (timed test on a stock deployment). Approver notifications and review-queue SLA/escalation both depend on it; interim: explicit notifications from the service.
  4. Schema evolution: working manifest migrations. Verified by probing: the deployer refuses a column drop, demanding an explicitly declared migration, yet the server ignores the manifest migrations key entirely — even junk content changes nothing, and the expected migration syntax is documented nowhere a plugin author can reach. Column drops are therefore impossible (unused columns must stay declared) and renames are drop+add. Provide a worked, honored, documented migration path before the registry's first breaking change.
  5. Sub-entity handling for system-created FuncCalls. Frozen catalog copies land in the same run history as personal saves; hiding them is a client-side filter on an artifactsFrozen option in Compute2's history listings only (Compute1 untouched). Server-side sub-entity semantics would hide them from every listing at the source.
  6. FuncCall list performance & shape. Measured: a filtered functions.calls list request has a ~1.5 s floor even at pageSize 20; there is no count endpoint and no bulk/where-based delete. Compute2's History panel pulls a function's runs unbounded, so its latency grows with the function's total run count — needs server-side newest-N paging/ordering.

Bugs

  1. Silent no-op delete on a scoped FuncCall miss. grok.dapi.functions.calls.delete(fc) resolves OK and deletes nothing when the call belongs to another package version (the source scopes to the current version's func); allPackageVersions().delete(fc) works. A scoped miss should be an error, not a silent success.
  2. FuncCall mis-wrapped inside object parameters. Passing a DG.FuncCall through the grok.functions.call boundary inside an object-typed parameter re-wraps it wrong on arrival (shaped like a DataFrame wrapper, no .options); typed funccall parameters work. Fix generic dart-object re-wrapping, or document object params as unsafe for entities.

Normal

  1. Declarative column immutability. An immutable manifest flag — today immutable columns are app-layer convention plus audit-based detection.
  2. Grants export / access-review reporting. Grants are listable per object only; a platform-level export across all domain schemas/tables/property schemas would provide access-review evidence (see the compliance table).
  3. Documented backup/DR for on-prem. Postgres + platform file storage (uploads, published dataframes) restore runbook; only cloud file-storage backup is documented today.
  4. Classic grant API parity. Entity permission granting is binary View/Edit while Share/Delete are checkable but not grantable — limits revocation tooling and delegation. Verified additionally: grok.dapi.permissions.grant refuses promoted domain rows ("no permission to share"); the public shares route works on them, but addresses groups by name only — promoted-row grants need a typed, id-addressed surface.
  5. Value-conditional column security. Transition rules like "block approved→pending" and "author may not approve own row" are inexpressible; the design dodges the former by keeping authors off status entirely, and covers the latter only as a service-side check.
  6. Awaitable registry-ready signal for JS apps. Verified: DomainView.create called from an app function during client boot intermittently fails with a NullError in refreshGrid — the view's column set draws on entity-type/property-schema meta still loading, and a not-yet-loaded column comes through as null. The platform's own /domains routes are sequenced after that load; a JS app has nothing to await (REST warm-ups do not populate the Dart-side cache) — the shipped workaround polls the entity handler's Dart-side meta before creating the view.
    Re-verified 2026-08-20: the registry-meta poll alone is NOT sufficient — cold deep links still intermittently die with NullError in DataSourceCardView.refreshGrid (DataFrame.fromList on null) and loadNextPage, leaving a dead grid that refresh() cannot revive. Pre-registering the per-table metas (grok_DomainRowMeta_RegisterPerTableMetas, awaited in the watcher) makes the view recover on its own in practice (error still logs), and the package adds a transplant fallback: if no grid canvas materializes within 8 s, a freshly created view is mounted into the docked root. The real fix stays core-side: the cold-boot grid build should await its own dependencies.
  7. Per-table UI affordance control in Domain Views. The auto "New <singular>" row-create button cannot be suppressed via the manifest (no such flag), and revoking insert permission instead would break the publish service, which inserts rows as the current user; singularName only fixes the label.
