Artifact Catalog Walkthrough

Publishing a Compute2 model run freezes an immutable copy, aligns it with a drug program, study, and molecules, and makes it discoverable in one shared catalog — trimmed to what each person is allowed to see. This walkthrough recreates the UI as annotated slides and follows four roles through the four core journeys. Every screen below is a mock recreation with sensible sample data — not a screenshot.

① Browse tree

One tree for the whole workflow: your own publications, the review queue, a node per drug program, and the shared registry of studies and compounds.

② Catalog views

Each view answers one everyday question. The catalog and the program pages show approved work only; the Review queue holds whatever still needs a decision; My publications is your own work and its current fate. Cards or a grid — with search, sorting, and filters built in.

③ Context panel

Clicking a program shows its properties and the three audience-group links — this is where members are managed. Clicking a publication shows its details, actions, and history (journeys 2–3).

Shareable links

Every view and program page has a stable link — paste it in chat or a meeting note and a colleague lands exactly where you are.

Code is the anchor

Context from the portfolio

Members-only visibility

Each program is visible only to its own audience groups — people outside the program never see it or anything published into it.

viewer ⊂ contributor ⊂ approver

Tiers nest: the Contributors group is itself a member of Viewers, and Approvers a member of Contributors. Adding a member to Approvers alone gives them everything below it.

Approval is a membership

There is no separate "approve" permission to configure — being in the Approvers group is what grants the right to approve or reject. Everyone else can read but not decide.

Member management

The group links open the standard member editor — adding or removing people is ordinary group administration, fully auditable.

What OK actually does

Behind the "Publishing…" progress bar, the catalog freezes an exact, stamped copy of the run — that copy is what gets shared and reviewed, unchangeable from this moment on. The working copy stays the author's, private and editable.

Field behavior

Molecules suggests the program's linked compounds (registration codes; typing searches the registry). Tags suggests existing tags and a new name creates one. Study lists the chosen program's protocols and resets when the program changes. Workstream defaults to modeling.

pending, because the publisher is a contributor

Every new version starts out pending. When an approver publishes their own run it goes live instantly; a contributor's publication waits for a reviewer.

⚠ Notification gap

The design calls for notifying the approvers group at publish time — but the platform's domain-table watch channel currently delivers nothing to the feed. Until that bug is fixed, reviewers must check the Review queue themselves. Only the balloons marked "works today" actually appear.

One queue for everything undecided

The Review queue gathers everything that still needs a decision — pending and rejected items — across all programs the reviewer belongs to.

Open artifact first

Open artifact opens the frozen run in Compute2 — the reviewer sees the actual model outputs, not just metadata.

Who can decide

Approve and Reject are visible to anyone looking at a pending item, but only members of the program's Approvers group can actually use them — and never on their own publication.

What the card shows — and hides

Cards lead with name · version; the status line appears only when a row is not approved ("approved is noise on a card"). Internal ids never surface.

One current version per publication

Approving records who decided and when, and makes this the single version readers see — an older approved version, if there was one, moves to history automatically.

Curate…

After approval, contributors can still fix discovery metadata (tags, molecules, path, workstream, description) via the Curate publication dialog — identity and approval fields are deliberately excluded from it.

⚠ Author isn't notified

The author learns about the approval from the balloon only if watching live, or from My publications — the feed notification shown above is not delivered today.

Same name, same publication

Publishing under the same name, program, and study means a new version of the same publication — the dialog notices while you type and says exactly what will happen.

Metadata copies forward

No downtime for readers

A reason is mandatory

A rejection can't be saved without saying why — and the reason stays attached to that version, in history, for good.

Rejected ≠ gone

The rejected v2 stays live — visible in the Review queue and in the author's My publications — until a resubmission archives it. Approved v1 is untouched; the audience keeps seeing the last good version.

⚠ The author finds out by looking

With feed notifications not working, the rejection (and its reason) is only visible in My publications / the Review queue — worth knowing when you set team expectations.

Three clicks, one answer

Molecule GRK-1234, study ABC-301, and a word of the name — the current approved version is the only thing left on screen, one click from opening.

Viewer tier, viewer buttons

A viewer sees Open artifact and history — publishing into the program is denied for viewers, and approval actions never apply to an approved row.

⚠ No structure search

Molecule filtering is by registration code, not chemistry: substructure / similarity search is an explicit design limit. The bridge is chemistry tooling — resolve a structure to registration codes there, then filter here. (Structures still display throughout the catalog.)

•

Out of scope for the PoC

🧩 More artifact types

The PoC publishes workflow runs and function runs. Other artifact types — dashboards, queries, reports — and richer filtering by artifact type are out of scope, mostly for technical reasons: each type needs its own way of being frozen and shared before it can join the catalog.

💬 Chat about a publication

There is no conversation around a publication — the reject reason is the only written exchange the workflow carries. Technically, publications are catalog rows rather than platform entities, so entity features like comment threads don't attach to them.

🎯 Finer-grained permissions

Access is granted per program — whole-program or nothing. Narrower scopes, such as one specific study or one model type, are out of scope: they need more research, are much more complicated technically, and would be hard for administrators to manage day to day.

•

Known gaps (this is a PoC)

🔔 Notifications don't reach the feed

Every dashed 🔔 card in this document is designed but not delivered — a platform limitation; only the balloon messages work today. Until that's fixed, reviewers check the Review queue and authors check My publications themselves. There are also no review reminders or escalation yet.

🔒 Security edges

A few edges remain open in the PoC: contributors aren't yet limited to their own programs for direct data changes, and frozen copies aren't yet locked down as tightly as designed. Each gap is tracked by an automated check that flags the moment the platform closes it.

🎛 UI customization isn't there yet

The catalog is built from the platform's generic data views, which can't yet be tailored to this workflow — built-in controls that don't belong here can't be hidden, and the standard dialogs can't be adapted. Closing this is a top item on the platform ask list in the package design doc.
