# datagrok-api changelog

## v.next

* GROK-20799: Added `grok.meta.propertiesOf(type, {filterable})` — the curated property catalog of a platform entity type or a domain table, as descriptors whose names filters, facets and grids accept; null for an uncurated type or an unknown table
* GROK-20799: Added `grok.meta.coreLocationOf(type)` — the read-only `Core` domain table serving a platform type's rows, or null
* GROK-20799: Added `Property.refType` (the type an entity-valued property points at) and `Property.relationKind` (the new `DG.RELATION_KIND` enum; null when the property carries no database annotation)
* GROK-20753: Added `DG.SEMTYPE.FUNCTION_NAME` (`'FunctionName'`) — the standard semantic type for a namespace-qualified function name.
* GROK-20753: Added `FuncCall.evalParamValidators(name)` — runs the parameter's named `validators:` against its current value in the call (resolution and evaluation stay Dart-side; passing validators are omitted from the returned `{message, isError, isHelper}` list).
* GROK-20753: Added `DG.StringUtils.levenshteinDistance(a, b)` / `jaroWinklerDistance(a, b)` — normalized string distances in [0, 1] (moved from `@datagrok-libraries/u2`)
* GROK-20753: Added `ui.pickTableFromFiles()` / `ui.pickTableFromQuery()` — open the platform's table-picker dialogs ('Select a file' over the file shares tree / 'Select a database query'); resolve with the picked `DataFrame`, or `null` when the dialog is closed without a pick.
* GROK-20753: Fixed `ColumnGrid` column callbacks receiving unwrapped Dart columns — the `create`/`popup`/`columnSelector` filters, `isColGrayedOut`, `isChecked` and the `filter` setter now receive a wrapped `DG.Column` (like `Menu.singleColumnSelector` already did).

* GROK-20753: Added `DG.U2.Control.forElement(el)` — resolves a DOM element to the nearest u2 control owning it (every `Control` registers its root); the DOM → component door for inspectors, automation and tooling.
* GROK-20753: `DG.U2.Component.getProperties()` gained the accessor tier — a meta-declared prop backed by an accessor with a setter is now writable through the generated property (the setter carries the live behavior); signal-backed props write as before, plain data fields stay read-only.

* GROK-20753: Added `FuncCall.evalParamChoices(name)` / `evalParamSuggestions(name, text)` / `evalParamDefault(name)` — evaluate a parameter's `choices` / `suggestions` / computed `default` sources Dart-side (suggestions receive the typed text; `evalParamChoices` also returns `dependsOn` and, for `propagateChoice: all`, a `lookup` map).
* GROK-20753: `grok.functions.scriptSync(s, variables?)` — an optional variables map evaluates the expression over a fresh context built from the map (omitted keeps the shell-context behavior).
* GROK-20753: Documented `Property.options` as the tags ∪ FuncParam-options union `InputBase.getOption` reads (tags win); treat as readonly — writes stick only for FuncParam-backed properties without tags.

* GROK-20753: Introduced `DG.IPropertyMeta` — the pure property-metadata vocabulary (name, type, propertyType, inputType, min/max/step, choices, editor, category, format, friendlyName, …); `DG.IProperty` now extends it, adding the accessors (`get`/`set`) and behavior options, and both live in `entities/property-meta.ts` as the one canonical shape (`DG.U2` re-exports them; the u2 core's `PropertyLike` is gone).
* GROK-20753: `Property.js(name, type, options)` and `Widget.addProperty(..., options)` now honor `options.get`/`options.set`: they become the property's real accessors instead of the default `x[name]`/field closures (and are no longer pushed into the Dart property mixin as plain values). `addProperty`'s change notification (`onPropertyChanged`) still fires around a custom setter, and a `{get}`-only options keeps the default `fieldName` write.
* GROK-20753: u2core protocol cleanup: `WidgetLike` is deleted — its contract is `DG.U2.Component`'s own surface, which `DG.Widget` answers by inheritance; `BindPropLike`/`BindSourceLike` are renamed to `BindProp`/`BindSource`; `ComponentMetaLike` is renamed to `ComponentMetaBase` (u2's spec-layer `ComponentMeta` extends it).

* GROK-20753: Introduced the `DG.U2` namespace — the u2 reactive core (signals, `Scope`, `Component`/`Control`, `dfBindings`) now ships inside datagrok-api (`import 'datagrok-api/u2core'`; plugins map it to `DG.U2` via a webpack externals entry so one instance is shared with the platform).
* GROK-20753: `DG.Widget` now extends `DG.U2.Control` — every widget gains `scope`, `own`, `bindStep`/`bindProps`, `componentMeta`, `specProps` and the property tier (`propertyTier`/`propertyTarget`); `detach()` also disposes the widget's scope.
* GROK-20753: `IEventType`/`IRectBounds`/`IInputStatus`/`IWidgetStatus` now live in `DG.U2` (u2core) as the single canonical definitions, re-exported unchanged from `datagrok-api/dg` (the `*Like` duplicates are gone; `value`/`choices` stay `any`).
* GROK-20753: `Widget.scope` is minted on first access — a wrapper that never engages u2 owns nothing, and reading `.scope` (not just `own`/`effect`) engages the widget's lifecycle (for a Dart-owned widget: the kill-walk cleanup and `own(kill)`).
* GROK-20753: Behavior change: `detach()`/`dispose()` on a Dart-owned viewer now kills it through the platform kill-walk (previously the Dart side was left alive).
* GROK-20753: Compile-compat change: `Widget.name` (via `Component.name`) is now an accessor pair — a `Widget` subclass declaring `name` as a plain field fails with TS2611 against this version; declare it as accessors instead.

* GROK-20752: Rebuilt the Node.js dart2js runtime bundle (`src/datagrok/build/web/grok_shared.dart.js`) from core master. It predated the `dateTime:raw`/`dateTime:int` None fix, so once grok_connect started choosing the component encoder (id 2), any query result with a datetime column holding empty values died under Node with `NullError: method not found: '_value' on null`. Any change to `ddt`/`grok_shared` decoding needs this bundle rebuilt in the same commit — the browser gets the freshly compiled client, Node gets this committed artifact.

* Added `grok.dapi.impersonationToken` — act as another user with a token you already hold (a signup response, a service token). The browser session is an HttpOnly cookie that script can neither read nor overwrite, so assigning `grok.dapi.token` same-origin does nothing; this sends the token in the `Authorization` header, which the server reads ahead of the cookie. It can only use a token already in hand, never the session's own JWT. Always clear it in a `finally` — while set, every call runs as that user.

* GROK-20298: `DomainFrameEditor`, `DomainGrid`, the unsaved-changes prompt (`confirmDiscardChanges` / `promptUnsavedChanges`) and the widget-action Func vocabulary moved INTO the platform (`DG.*`, `src/ui/domains/`), so every session can edit a domain grid with no package installed. They are the same classes `@datagrok-libraries/domain-ui` exports — it now re-exports them, and every existing import keeps working. What would have been generic top-level names on the `DG` surface are STATICS of the class that owns them: `DG.DomainFrameEditor.STATE_COLUMN` / `.CHANGES_COLUMN` / `.ERRORS_COLUMN` / `.SERVICE_COLUMNS` (one shared `readonly string[]` per session) / `.validateCellValue` / `.isReferenceProperty` / `.editorsOf`, and `DG.DomainGrid.saveFunc` / `.discardFunc` / `.resetFunc` / `.addRowFunc` / `.deleteRowFunc` / `.refreshFunc` / `.widgetActionFunc` / `.actionFuncName` / `.WIDGET_ACTION_NAMESPACE` / `.WIDGET_ACTION_TAGS`. `DomainSaveResult` carries the `inserted` / `updated` / `deleted` counters — ids and versions land back in the frame, and a host that keeps its own row objects re-queries after a successful save — and `DomainFrameEditor.attachTo(dataFrame, schema, table)` attaches to a frame a host already owns; a host whose refresh rewrites row values in place calls `DomainFrameEditor.clearSnapshots()` so pre-edit snapshots cannot record the old rows as edit originals.

* GROK-20298: `ObjectHandler.renderMarkup`/`renderTooltip`/`renderCard`/`renderListItem` now receive the `context` the caller passes all the way into the platform (Dart) handlers — `EntityMetaDartProxy` used to drop it. The Dart side takes it through new context-aware members (`ElementRenderer.renderMarkupFor` & co), and the `grok_Meta_Render*` entry points gained a trailing OPTIONAL context argument, so handlers and call sites that ignore it are unaffected.
* GROK-20298: A relation's `'<relation>.id'` filter leaf now asks about the link SET, not about one link — it is what the relation facet's checkboxes emit: `!= [id, ...]` EXCLUDES the owners linked to any of them (the uncheck gesture), where the per-hop reading would have kept an issue tagged `[bug, urgent]` right after `bug` was unchecked. `= null` / `!= null` (the "(no value)" bucket) are unchanged, and single-valued FK paths are untouched.
* GROK-20298: Documented many-to-many relations on domain tables: a declared relation is an expand key returning `DomainRelationLink[]` (`{id, name}`, capped at 100, ordered by display name) on `query`, a chips column plus its `'~<relation>.id'` companion on `queryDf`, a filter/facet path (`'labels.name'`, `'labels.id'` ANY-of, `'<relation>.id'` categories with display names), and a list of target ids on `insert`/`update` — where it has SET-REPLACE semantics **over the links the caller can see** (`[]` clears them, an absent key leaves them untouched, invisible links are never removed). `batch` refuses relation keys. `DomainTableClient` gained a fifth, defaulted generic `TUpdate` (default `Partial<TRow>`) typing `update()` and `updateWithRetry()`'s mutate result, so `grok api`-generated clients accept their `<Table>Update` payload; untyped callers are unaffected. Relation paths work in the smart-filter STRING form too (`'labels.name = "bug"'`), like any other path.
* GROK-20298: **Every** `DomainTableClient` now materializes datetime columns as dayjs on JSON reads (`query`/`get`/`getByKey`, recursing into `'details:'` child rows and covering `'<fk>.<col>'` master-expand fields) — the columns resolve from the domain registry (system `created_on`/`updated_on` plus declared datetimes), cached per table for the session. Untyped `table('s.t')` clients previously kept ISO strings — code comparing those fields as strings needs `dayjs` handling. Explicit `DomainTableClientOptions.datetimeColumns`/`detailDatetimeColumns` remain honored as an override (legacy generated clients keep exact behavior); new `grok api` output passes no config.
* GROK-20298: Added `ObjectHandler.renderInput(x)` — a meta-provided input for the item (e.g. for forms), null when the handler defines none. Bridged both ways across the JS/Dart boundary; the platform's `UserMeta` returns the user selector, so `ObjectHandler.forEntity(user).renderInput(user)` yields a ready-to-use single-user picker.
* GROK-20298: Added `ObjectHandler.renderListItem(x)` — renders the item as a list-item div, for displaying objects in lists (wide html grids, popups in type-ahead boxes); defaults to the item's name. Bridged both ways across the JS/Dart boundary: `EntityMetaDartProxy.renderListItem` calls the Dart meta (whose default wraps `renderName()`), a registered JS handler's override wins the Dart-side dispatch, and `DomainObjectHandler` delegates it to the platform meta like its other render members.
* GROK-20298: `DomainObjectHandler.pickRow` (static and instance) accepts `{anchor}`: with an anchor element the lookup picker opens as a headless drop-down below it, right-aligned (no caption or buttons; the picking click, an outside click, or ESC closes it); without one it stays the modal dialog. New `DomainPickerOptions` interface.
* GROK-20298: A JS `ViewBase` subclass now comes back from discovery as ITSELF — `DG.Widget.getAll()`, `DG.Widget.find(root)`, `grok.shell.v` and `grok.shell.preview` return the original JS object (they used to return a plain `DG.View` wrapper around its Dart host), so a page's `getWidgetStatus()`/`getFunctions()` overrides are reachable from discovery, the way they already were for plain JS widgets. NB for callers that relied on the wrapper: a JS view is a `ViewBase`, not a `View` — `DG.View`-only members (`dockManager`, `addViewer`, ...) are not on it.
* GROK-20298: `Widget.detach()` now unregisters the widget, so `DG.Widget.getAll()` / `Widget.find(root)` stop returning detached JS widgets (discovery used to keep the oldest one forever). Dart-owned widgets (`DartWidget`) keep their registration — that one belongs to the Dart lifecycle (`Widget.kill`).
* GROK-20298: Fixed `DG.Property.create` (and everything built on it — `Property.bool`/`int`/`string`/..., `Property.js`/`jsInt`/.../`fromOptions`): the `setter` argument is now actually callable — `p.set(obj, value)` used to throw ("is not a function") for every property created with one, because the Dart side wrapped it and handed the wrapper back unconverted. Property setters of properties with no setter still read as `null`.
* GROK-20298: `grok.functions.register({namespace})` now honors the namespace it is given: an unregistered name (a library's own vocabulary, as opposed to a package's) is registered rather than silently falling back to `core`, and a JS registration never overrides a function of the same name that it does not own — a same-named core function survives, with a warning instead of a silent clobber.
* GROK-20298: `grok.shell.preview` accepts and returns `ViewBase | null` (was `View | null`) — assigning a JS view no longer needs a cast.
* GROK-20298: `grok.dapi.domains.registry.tableInfo()` reports the table's `description` from schema.json (null when undeclared).
* GROK-20298: Additive machine-surface API: `IWidgetStatus` gained an OPTIONAL `inputs?: IInputStatus[]` field (`src/widgets/base.ts`), and the new `IInputStatus` interface (`{name, caption?, type, semType?, value, choices?, required, valid, error?, description?, ref?}`) describes ONE named input's live state — the name is the input's property name, so `widget.props[status.name] = value` writes exactly what typing into it would. Nothing existing changes: the field is optional, the base `Widget.getWidgetStatus()` implementation is untouched, and widgets that do not edit named values omit it.

* GROK-20298: Added `DomainObjectHandler.rowFrom(values)` — wraps one row of a `query()` result as a `DG.DomainRow` locally, without a round trip: the acquisition path a list, a card or a context panel uses to render, address and act on rows it already fetched (`getById` remains the one that asks the server). `newRow()` is `rowFrom(null)`. Anything but a plain values map (or null) is rejected by name — read key by key, a string or an array used to produce a row of nonsense values that only surfaced later, as a card with no identity.

* GROK-20298: `DomainObjectHandler.deepLink`/`openRow`/`copyLink` now reject a foreign object by name like the rest of the row members (they used to silently resolve null / do nothing); an unsaved row of the handler's own table still yields `null` / a no-op. The "not a `<table>` row" message renders the rejected value readably (its class name or JSON) instead of `[object Object]`.

* GROK-20298: `DG.DomainQuery` parity and doc fixes: a `'['`-prefixed filter element whose members are not conditions, nested groups, or `'and'`/`'or'` connectors is now rejected by `toSpec()` with the same message the `DomainQuery` function uses (it used to be handed on as a smart-filter string), and a negative `limit`/`offset` in `fromUrlParams()` throws instead of reaching a server that clamps it to 0 and returns nothing. JSDoc: `run()` states that the result is added to the workspace AND opened in a table view that becomes current, that the creation script is recorded only with `grok.shell.settings.dataHistory` on, and that its failures are the function's raw errors rather than typed `DomainError`s; `DomainQueryBuilder.toQuery()` states that an un-`top()`ed builder awaits 100 rows while its `toQuery().toSpec()` falls back to `DOMAIN_QUERY_ROW_LIMIT`; aggregate mode is documented as REJECTING `columns`/`offset`, not ignoring them.

* GROK-20298: Fixed two domain openers that could never settle: `DomainObjectHandler.deleteRow()` stayed pending forever when the delete FAILED (a restrict violation, a 403, a server error) or when the dialog was closed programmatically, and `showConflictDialog()` stayed pending on a programmatic close — both now resolve on the dialog's close (`false` / `null`), and `showConflictDialog` reports interop failures as typed `DomainError`s. The platform's own edit dialog no longer hangs either when the post-conflict reload fails. `DomainView.meta` now throws a named error explaining that the view takes its handler from the domain registry (it used to fail with an opaque `NoSuchMethodError`), and the handler members that need a row (`cloneRow`/`deleteRow`/`shareRow`/`showHistory`/`auditPane`) report a foreign object by name. JSDoc corrections: `query` reports the view's row CAP (re-running it reproduces what the view shows, it does not lift the cap), `query.filters` is omitted rather than empty, `shareRow` resolves when the sharing dialog is SHOWN, and a route-opened Domain View is a plain `DG.View` in JS (wrap it: `new DG.DomainView(grok.shell.v.dart)`).

* GROK-20298: Added `DG.DomainQuery` (`src/domains.ts`) — the single serializable representation of what a user is looking at: the `DomainQuery` function's parameters (`fromParams`/`toParams`, the same `DomainQueryParams` shape `DomainView.query` reports, now covering the function's full surface), a deep link (`toUrlParams`/`fromUrlParams` binding one URL key per list element — `filters[0]` — with the reserved `view=`/`entity=` UI params staying outside the query), a REST spec (`toSpec()` for a silent `queryDf`, always with an explicit limit), and `run()` — the reproducible path through the platform function, so the frame carries a creation script (Source-pane refresh, data sync, URL parameters). `DomainQueryBuilder.toQuery()` (and `DomainQuery.fromBuilder`) export the fluent builder's state, splitting top-level AND conjuncts into one filter element each.

* GROK-20298: Added `DG.DomainView` (`create({schema, table, permanentFilter, embedded})`, `showFilters()`, `query`) — the platform's Domain View for a domain table, creatable programmatically and embeddable, with the gallery/grid, search, sort, paging, filter panel and in-grid editing it has on `/domains`; it extends `CardView`, so `searchValue`/`permanentFilter`/`refresh` come from there (`renderMode` reads the current mode, but assigning it only sets the field — it does not perform the switch, a pre-existing `CardView` limitation; use the view's own mode switches). `query` reports what the user is looking at as `DomainQueryParams` (the `DomainQuery` function's parameter shape). Added the platform dialog/pane openers as `DomainObjectHandler` STATICS — `createRow`/`editRow`/`cloneRow`/`deleteRow` (resolving to whether the row was saved/deleted), `shareRow`, `pickRow` (the lookup picker), `showConflictDialog` (resolves `'reload' | 'overwrite' | null`), `auditPane`, `showHistory`, `grantsPane`, `showGrantsDialog`, `deepLink`, `openRow`, `openPath`, `copyLink`: each enters the SAME Dart flow the built-in surfaces use, and the instance members (which no longer reject as "not available yet") delegate to them, so a subclass replaces a flow by overriding one method. `openRow`/`copyLink`/the detail tabs' `open()` now go through the platform's own navigation and clipboard helpers instead of `grok_Route`/`navigator.clipboard`; `copyLink` and `showHistory` are consequently synchronous, and `shareRow` resolves `void`.

* GROK-20298: `ObjectHandler.renderGrid` now falls through to the platform meta from the JS side too: the base member delegates to the Dart meta registered for the handler's `type`, so `ObjectHandler.forEntity(x).renderGrid(grid)` decorates like the built-in view for ANY non-overriding handler (`DomainObjectHandler` no longer needs its own override). Also in `DomainObjectHandler`: `getRibbonActions` offers the platform's default `Open` action, gates `Share...` on the row's Share permission, and returns nothing for an unsaved row (whose `deepLink` is now null instead of throwing); `renderEditor` degrades to a read-only message without `canInsert`/`canEdit` (column security alone is not table Edit); `getDetailTabs().open()` builds its URL with the platform's own path builder.
* GROK-20298: Added `DG.DomainObjectHandler` (`src/domains-ui.ts`) — the reflective per-table `ObjectHandler` for domain rows: registry-driven `getProperties`/`getDetailTabs`/`renderEditor`, capability-gated `getRibbonActions`, `getById` (the first JS acquisition path for a `DG.DomainRow`), `newRow`, `deepLink`, `copyLink`, `setWatch`, and render defaults (card/markup/tooltip/properties/view/preview/grid) that DELEGATE to the platform's per-table meta — an override-nothing subclass renders exactly like the platform. Registration stays `DG.ObjectHandler.register()`, and the platform CRUD commands stay with it. Interfaces `DomainDetailTab`/`DomainAction`; the dialog openers (`editRow`/`cloneRow`/`deleteRow`/`shareRow`/`showHistory`/`pickRow`) reject with a clear message until `DG.DomainView` ships. Also: `EntityMetaDartProxy.getById` now delegates to the Dart meta instead of resolving null, and `splitDomainTable` (the `'<schema>.<table>'` contract) is exported from `src/domains.ts`.
* GROK-20298: Fixed `DomainRow.permissions()` on an unsaved row: an id-less row now reports no permissions for admins too (it used to advertise edit/delete/share on a row that does not exist yet).
* GROK-20298: Fixed `DomainTableCapabilities`: `canEdit`/`canDelete` no longer report a table grant that the server does not honor on rows (non-table security modes require the securing table's rows to default to table visibility), `DomainRow.permissions()` now rejects with typed `DomainError`s instead of a raw interop object, `registry.rowProperties()` returns display copies whose `friendlyName` matches what the platform renders ('Project', not 'Project_id'), and a failed capability probe is no longer cached (it used to pin the UI read-only for the session). JSDoc now states both drift directions of the capability flags.
* GROK-20298: Added domain registry reflection and permission-driven capabilities: `grok.dapi.domains.registry` (`rowProperties` — runtime `Property` metadata per table, `tableInfo` — display identity + FK-inverted `childTables`, `resolveNames` — batched display-name resolution), `DomainTableClient.capabilities()` (`DomainTableCapabilities`: server-truth canView/canInsert/canEdit/canDelete/canShareTable + writable columns, cached per registry generation + user), `DomainRow.permissions()`, and `grok.dapi.domains.invalidateUiCaches()`; grant/revoke/column-security calls through the client invalidate the caches automatically.
* GROK-20298: Added `ObjectHandler.renderGrid(grid, options?)` — customizes a grid presenting the handler's objects in place (column visibility/order, captions, renderers); the built-in Domain View grid dispatches through it, and any handler that does not OVERRIDE it (old or new) falls through to the platform default decoration — override with an empty body to opt out. `EntityMetaDartProxy.renderGrid` delegates to the Dart meta (new `grok_Meta_RenderGrid`).
* GROK-20298: `TypeAhead` (`ui.typeAhead`): `source` now also accepts an async callback `(query) => Promise<(string | {label, ...})[]>` for server-backed suggestions (a debounced self-contained dropdown; extra fields of picked objects reach `onSubmit` intact). The typeahead-standalone `local`/`prefetch`/`remote` sources work unchanged.
* GROK-20606: JSDoc sweep over the typed domain surface (caps, dayjs convention, bound-values rule, retry budgets, builder invariants); `DomainColumnRef` now folds in the system columns (`DomainSystemColumn`) so condition, sort, and aggregate column slots accept them even when a hand-written column union omits them (other slots stay TColumn-typed); `updateWithRetry` refuses to degrade to an unversioned update when the fresh row carries no version (typed `DomainError`, code 'no-version').
* GROK-20605: Fixed `save()`'s business-key-duplicate path — an id-less save whose key matches an existing row is now a TRUE insert-or-update: the caller's values are applied to the existing row as a versioned update (retried on conflict), and the resolved row carries the real incremented version. save() never resolves a version-less row; unversioned (last-write-wins) updates remain available only by deliberately constructing `{id}` without a version.
