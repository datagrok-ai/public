# U2 changelog

## v.next

* Designer: split the view into its layers behind the same surface — `view.ts` keeps the canvas and the wiring, `selection.ts` the selection model and hit-testing, `drag.ts` the mouse-drag layer, `actions.ts` the editing verbs, `keys.ts` the keyboard map, `ribbon.ts` the ribbon and its dialogs; the object handler into `handler.ts`, `prop-model.ts` (the property model) and `prop-editors.ts`. Names, signatures and import paths are unchanged
* Tests: introduced one module of getter-backed platform doubles (`tests/platform-doubles.mjs`) for the headless suite — every fake `Property`, `Func`, `FileInfo`, `DataFrame` or entity row keeps its state on `dart` behind prototype getters, as the real one does, and the module pins it; the loader hooks serve these same classes
* E2E: split the designer checks into per-feature files under `e2e/checks/`, each opening on its own fixture, ids numbered per file; `npm run e2e:local -- --only <feature>` runs one
* Sources: extracted what the five sources shared — the async pair's status projection and `state`/`error` steps (`AsyncSteps`), the start()-time bind resolution (`subBind`) and the backend guard (`requireBackend`)
* Entity ref: fixed the binding picker offering `dart` — the raw Dart handle a platform entity keeps as its one own field — as a leaf of every `u2-entity-ref`

* Designer: the spec a host hands over is a constant, not the designer's document. `SpecDesigner.open()` — the one funnel the constructor, New form, the samples, the gallery and the Open dialog all go through — copies an object input once, so the editor's in-place patching (DD10) can no longer reach it. A host that passes a module-level literal, as `u2DesignerApp` does with `DESIGNER_SPEC`, was getting it progressively edited: close the designer, reopen the app, and the next one came up on the previous session's work

* Build: `npm run build` now fails on a stale `manifest.json` (`npm run manifest:check`) and on any `var(--dg-…)` naming a token no sheet declares (`npm run lint:tokens`, reported as `file:line`). The manifest stays checked in — the gallery fetches it, the recipes point at it, and it ships in the npm tarball — so the fix for its drift is a freshness gate, not gitignoring it; the token lint exists because `var(--dg-text-light)` shipped as a silently inert rule that nothing in the toolchain could see

* Designer: a file or a query dragged out of Browse becomes a data source. Dropped anywhere over the designer it lands on the tray — the same Delphi gesture the palette's non-visual drag already made — as one `u2-func-source`: a file over the platform's own `OpenFile` with its `fullPath` (a path reopens on any client, where an open table's name does not), a query or function under the name a spec can call. A multi-selection drops as many sources in one gesture and one undo step, and the first of them is selected
* Designer: a dropped file is read once on arrival, through the same Refresh path the tray chip offers, and the balloon says what came of it — the drop is the explicit act DD9 permits, and a source with no visible pulse reads as broken. Nothing else a drop carries is run: a hand-written query is inserted and left for Refresh, exactly as it is when it is picked by hand
* Designer: a dropped file nothing can open as a table is refused BY NAME, with the extension in the message — the drag itself is accepted so that the refusal has somewhere to appear. Refusing at `acceptDrag` is what makes a drop fall through in silence, which is the worst possible answer to "why did nothing happen". What counts as tabular is the text formats, `d42`, and every extension a registered `file-handler` declares — read per drag, so a package staged later in the session counts

* Designer: a tabs or an accordion dropped from the palette arrives with one pane — `Tab 1`, `Pane 1` — instead of an empty box with a 'Drop here' hint and no tab strip at all, which showed the user nothing of what they had just made and gave them no header to click. A splitter seeds two panels: one has no sash to drag. Registrations declare them as `ComponentMeta.defaultChildren` (plain JSON, in the manifest), deep-cloned and uniquely named per insert, and they ride the container's own patch — one undo takes the whole thing back, and the first 'Add tab' counts the seeded pane and produces `Tab 2`
* Designer: the binding picker never opens onto silence. A source that has not run knows no columns, so `currentRow` expanded to nothing at all — no message, no spinner, nothing to tell a data source that is empty from one that is broken ("I genuinely thought my data source was broken"). Any walkable step that enumerates empty now carries one explanatory child, and it is not pickable
* Func source and entity ref: an explicit Refresh runs the source whatever the design-time policy says. The engine used to exist only under `live`, so on everything else the tray's Refresh — the one run DD9 does allow, because the user asked for it — reached a source that had nothing to run and did nothing at all, silently. What a run brings back outranks the preview it replaces
* `AsyncValue.refresh()` starts the run now instead of behind the debounce, and answers when it lands. The debounce is there to coalesce dependency changes; sitting on the user's own ask is what made a Refresh look ignored
* Designer: a Refresh says what came of it — `orders: ready · 4 rows`, or the error the run ended with. A source whose refresh answers nothing (a pager's) is watched until it stops loading, so the balloon names the result and not the wait
* Designer: the context panel of a data source shows its pulse — state, how much it holds, the message when it failed, and, for the sources that have no `designData` at all, that they are always live. It is the one live section of the panel: a source runs on its own clock, and until now the canvas showed the same empty fields whether it was loading, was never run, or had failed. The tray chip follows the same status in its class and its hover text
* DataFrame bindings: a `currentRowIdx` past the last row reads every `currentRow.<column>` as empty, in both directions and from any state. The fields used to keep the last row that DID exist, sitting there as if it were data — and the frame is no longer moved to an index it cannot hold, which threw `Row out of bounds` and took the field refresh down with it
* Func source: the `sample` preview is built once and kept. It was rebuilt on every read of a dependency-free computed, so every binding under it pointed at a frame nothing else referenced
* Designer: the Bindings and Events sections fold. One row per bindable prop is a lot of panel for a node that binds nothing, and it pushed Events past the bottom of the platform's property pane — which scrolls with no scrollbar and no fold shadow, so the section simply was not there. Bindings opens when there is wiring to see and folds when every row is an empty invitation; Events, the section it was hiding, stays open
* Designer: an Events row says it picks a FUNCTION — the field's own hint and the `…` beside it, which the dialog it opens has said all along

* Designer: the binding picker's search reveals what it matched. A match used to arrive inside branches the picker then left closed — three levels to open by hand, every keystroke — and clearing the box collapsed every one of them again, because the rows were re-keyed per query and the tree's expansion is keyed by row. A row id is now the node's own place in the tree: the branches down to a match are opened for it, a match keeps its whole subtree (it is what was asked for, so the filter stops there), and clearing the query keeps open what the search opened
* Designer: both pickers say when nothing matched — a blank white box read as a dialog still loading, twice, in two separate acceptance passes
* Designer: the binding picker groups its roots under the heading that says where they came from — App data (the app that opened the designer), Data sources (the tray) and Form controls — so a brand-new empty form no longer offers two names out of nowhere with nothing to explain them
* Designer: the function picker draws its own rows — icon, caption, name and description on one line — instead of the platform's entity markup, which drew the icon on top of the caption and let the descenders fall outside the row. The description is on the row because the search matches it: `record` used to return two functions with the word nowhere in sight
* Designer: the function picker offers only what a spec can call. `Func.find` also answers registrations keyed by a path (`/molecule.json`), which no `cmd:` can name
* Designer: `bindPickerButton` takes the tooltip its row needs — an Events row opens the function picker, and said "Pick a binding" while doing it

* Func source: a design-time auto-run is limited to VISUAL queries — the class the row cap actually covers and the only one that is known to read. `DG.DataQuery` also covers hand-written SQL, and GrokConnect executes what it is given, DML and DDL included, so opening someone's shared spec used to run whatever that query does with no user gesture at all; a hand-written query now waits for the tray's Refresh exactly as a script or a function does. The backends seam grew the `table-query` kind to say the difference (DD9/Q5/Q9 amended by the P4 review)
* Source backends: the design-time row cap is serialized per query entity. `TableQuery.limit` lives on the SHARED query, and the platform cannot cancel a run, so two overlapping design-time runs interleaved: the first restored the limit the second had just set, and the query was left capped at 100 rows for the rest of the session — including when the user opened it themselves. Only the first run captures the previous limit now, and only the last one puts it back
* Entity source: a filter that comes from a BOUND value is sanitized before it reaches the server's smart-filter grammar — that value is whatever the user typed into an input. The literal `filter` prop stays raw: the author of the spec writes it, and writes it in the grammar
* Spec: a tray component is owned by the instance, never by whatever scope is ambient when it is built — a patch committed while the context panel was constructing its form handed a live data source to the panel's scope, and the next panel disposal killed a source the form on screen was still bound to
* Spec: a component is started once per change, however many ways it was reached. A source whose param binds to another source is a dependent that is itself a component: the Design/Run toggle re-mounted it and then re-rendered it again as a dependent, so `start()` — which is not idempotent — ran twice, registering its effects twice and doubling its listing and count requests for the session
* Func source and entity ref: the failure is a binding step — `$.orders.error` is the message the run or the lookup ended with, so a form can say WHY it is empty instead of looking exactly like one whose query returned nothing
* Spec: the default-binding walk is depth-bounded like the picker's own — a source whose `bindStep('')` answers itself no longer spins in the renderer
* Designer: the tray's entity-collection dialog owns its inputs through the tray's scope, like the function wizard beside it — closing it any other way than OK or Cancel used to leak them
* Func source: a function's outputs are enumerated field by field instead of by copying the platform property — a `DG.Property` keeps everything on prototype getters, so the copy was an empty object and every output showed as a nameless, untyped row in the binding picker, unpickable and unwalkable. The fake runner the headless suite uses hands out plain objects, which is what hid it until the designer was driven against a real package function
* Designer: the whole walk is covered end to end — a new e2e check builds a working master-detail form from `New form` with zero hand-written JSON (the tray wizard for the data, the palette for the controls, the binding picker for the paths, the function picker for the button), round-trips it through its own dump, and then proves the `schema` policy empties the preview while running nothing: a spy over `grok.functions.onBeforeRunAction` and one over the page's requests, not a look at the canvas
* Designer: the stand lane gained the two checks canned data cannot answer — an entity source listing the users that server actually holds, and the design-time 100-row cap surviving a real query execution (the check creates the visual query it needs and removes it again)
* Designer: the function picker — one dialog over every function the client registry knows, searched by name, caption and description (`Func.find`'s own name is an exact match, so the search is one enumeration and a local filter), rows drawn by the platform's own entity handlers, and the picked function's inputs as an arguments form: a typed editor per param, or the binding picker beside it for the ones that follow a value. It opens from the Events section of the context panel (the `…` beside the hand-editable command field) and from the tray's source wizard
* Designer: an event picked this way is written as one patch — the plain `cmd:name` string while there is nothing to pass, the structured `{cmd, args}` form otherwise, with a literal that looks like a path escaped once (`$$.`) and a bound argument left as its path
* Designer: a source that names a function gains a Parameters section in the context panel — one typed editor per input the function declares, every edit coalescing into the one `params` prop (a whole pass is one undo step), and a `…` per row writing the dotted `params.<name>` sub-bind through the same funnel a typed path takes; a bound param shows the path it follows, read-only, and is cleared in the Bindings section below
* Designer: the tray gains a `+` menu — the tables already open in the workspace (picking one inserts a `u2-table-source` named after the table, with the by-name caveat said out loud), a function or query through the picker, an entity collection through a small dialog, and a state variable. Each ends in exactly one `add-component`, seeded off the tag's defaults; a picked function's literal arguments become `params` and its bound ones the dotted keys, and `designData` is deliberately left unseeded — the source computes the policy from the function's kind
* Spec: a re-mounted component is started only once everything the same change re-renders has been rendered again — the two phases construction already had, on the way back. A dependent's re-render promotes to the container that adopts it, which rebuilds every input under it; a source started before that held the signal of an input nothing shows any more, so a param bound to an input stopped re-running the source after a Design/Run toggle or a prop edit
* Added the four platform-backed data sources (src/sources/): `u2-func-source` runs a function, query or script and exposes its outputs — a DataFrame output walks the whole frame surface, and a single-table source answers those steps directly, so `$.orders.currentRow.name` is the master-detail bind; `u2-entity-source` pages a `grok.dapi.*` collection into `items`/`names`/`state`/`total` with `refresh`/`loadMore`; `u2-table-source` follows an open workspace table by name; `u2-entity-ref` looks one entity up by id and answers its properties as binding leaves. All four register `visual: false` under the palette's Data pane
* Func source: a param takes a path of its own through the sub-bindable `params` prop (`"bind": {"params.days": "$.daysInput"}`), resolved once the whole form exists, and the source cancels and re-runs — debounced — whenever a bound param changes; `refresh` is a component function, so `cmd:orders.refresh` wires a button to it
* Design-time policies (DD9): `designData` is `live` (real runs, capped at 100 rows), `schema` (never runs, still enumerates the declared outputs) or `sample` (built from the `sample` prop stored with the spec, or the tag's `designPreview`, with rows going through `DG.DataFrame.fromObjects`); a query defaults to live and everything else to schema, and a function that is not a query is never auto-run at design time however live the policy — the tray's Refresh is its only run
* Added src/dg/source-backends.ts: fills the sources' platform seam at dg import — `DG.Func` lookup and `prepare(params).call()` (the design-time cap through `TableQuery.limit`, held across the whole call because the platform reads it as the query EXECUTES, and serialized per query entity so overlapping runs cannot leave it set; a plain-SQL query or an arbitrary function has no FuncCall-level cap to honor, and the platform offers no cancellation either — a superseded run finishes and its answer is dropped), a curated `grok.dapi.*` collection map, `grok.shell` plus onTableAdded/Removed for the workspace, and `DG.DataFrame.fromObjects` for samples
* Choice and multi-choice inputs: `items` is bindable, so a data source feeds a picker directly (`"bind": {"items": "$.people.names"}`) and the list follows the signal instead of being copied once
* Inputs: a bound source holding nothing yet — a data source before its first run — leaves the field empty instead of showing the literal "undefined"
* Designer: the binding picker — a `…` button beside every path field opens a dialog holding the tree of everything the form can bind to (context data, the tray, then the named controls, each expanding through `bindProps()`), with one search box over the labels; a leaf answers its assembled path (identifier steps dotted, anything else bracketed and escaped), a walkable step is a group that commits nothing on its own, and the commit takes the same funnel a typed path takes — `canApply`, then `set-bind`, or a warning naming the loop when the path would close a binding cycle. The tree is lazy by contract: enumerating a frame's columns allocates no column signal
* Designer: the Bindings section renders one row per bindable prop, bound or not (plus anything the node binds beyond them — a dotted sub-bind key, a prop of a tag the registry no longer knows), so a binding is ADDED there instead of only corrected; the path field stays hand-editable, and a bound prop stays read-only in Properties
* Added `bindTree(instance)` / `filterBindTree(nodes, query)` (src/dg/designer/bind-model.ts): the picker's model, pure and platform-free — lazy children thunks, `walkable` driving expandability, `writable` shown as ⇄, and type plus semType in the leaf label
* Spec: the envelope gains the non-visual tray — `components: SpecNode[]`, validated by `parseSpec` and emitted by `dump()` BEFORE `root` (what the form binds to is declared first, and an emptied tray goes with its last entry). Construction is two-phase: every component is built first, so a visual bind resolves against it, and `start()`ed after the whole form exists, which is where a source resolves the params bound to inputs. A component takes no children (warned and dropped), warns once when it has no name to be bound to, and maps the same `u2-spec-error` placeholder when it cannot be built — counted, selectable and undoable like any other node; `nodes()`/`node(name)` widen to `Component | HTMLElement`
* Spec: `SpecInstance` gains `designTime` (constructor option) and `setDesignTime(x)` — the designer's Design/Run toggle rebuilds every component for the mode and renders everything bound to one again, without touching the edit history (the mode is view state, not document state); `rerenderAll(nodes)` and `renderRootOf(node)` are the one authority on render-root promotion, which the editor now calls instead of computing its own
* Registry: `visual: false` + `createComponent(props, env)` register a non-visual component (`create` is optional now, and register-time validation says which factory a tag needs); `ComponentEnv` carries `designTime`, the node's raw binds and a `resolve` deferred to `start()`; `designPreview` joins the metadata; the manifest strips `createComponent` and carries `visual`/`designPreview`
* SpecEditor: `add-component` / `remove-component` (structural, mirrored inverses, no move — chip order is cosmetic); `canApply` refuses a data source in the form and a control on the tray while letting an unknown tag land in either (containment); names are unique across both trees; and any patch on a component extends the re-render to every rendered node whose bind or event references it — otherwise a rebuilt component leaves its consumers wired to the corpse. `referencesOf(spec, name)` (in src/spec/path.ts, beside `findBindingCycle`) is the read-only sibling of `renameRefs`
* Added `u2-state` (src/sources/state.ts): the value a form owns — one writable signal several controls share, a type-checked `initial` it starts at and a `clear` function it returns to; `$.draft` binds it two ways through the default step
* Designer: the components tray — a chip strip along the bottom edge in design mode, one chip per component carrying its name, tag tooltip, broken and selected styling, and `data-u2-name` (a component has no canvas element, so the chip is its automation handle); a click selects through the ordinary pipeline, a right-click opens the same action menu plus 'Refresh' where the component declares it, and the structure tree lists the form first and the tray after it. Palette items registered `visual: false` group under a 'Data' pane, and dragging one anywhere over the designer highlights the tray and lands there
* Added the binding path grammar (src/spec/path.ts): `parsePath` over `$.first` plus `.ident` / `['quoted string']` steps (with `\'` and `\\` escapes; anything malformed answers null rather than throwing), `segmentsToPath` as its exact inverse for the picker, and `findBindingCycle(spec)` — a DFS over named nodes' and components' bind first segments that answers the loop, closed, or null

* Spec: a two-way bind to a read-only leaf (a computed) keeps the one-way bridge and warns once instead of silently doing nothing (`isWritableSignal` in core/signals.ts is the gate — a prototype-descriptor check, so the vendored `Computed` classifies read-only without engine knowledge); a hand-written binding cycle renders its members broken with the loop named
* Spec: `cmd:` tiers (DD6) — `cmd:#name` is reserved for code-behind and warns, a name containing `:` calls the context's new `callFunction` hook, a dotted `cmd:orders.refresh` applies that named component's `getFunctions()` entry, and a bare name is a context command falling back to `callFunction`; events widen to `SpecEventEntry = string | {cmd, args}`, whose args resolve when the event fires (`$.` paths peeked untracked, `$$.` unescaped once, everything else literal) and deep-copy through `dump()`
